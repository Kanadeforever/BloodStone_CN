- R10.4 主汉化继续只负责字体/LOC/GetText/SubmitText，不再包含 NPC 字幕代码。

- 英文版 fallback 不内置英文翻译表，而是从 `0x00F12820` 的运行时返回对象中探测原版英文文本，并捕获游戏自己的原生字体/纹理来绘制。

- 0.2 默认 `BaseY=0.120`，新增 `LineSpacing=0.82`，同时收紧多字幕事件的垂直步进。
- 0.2 首次实机出现“启动后字幕完全不显示”；日志证明 Dialogue/LOC/queue 全 PASS，但没有任何 CreateDevice/Reset/EndScene/BFA_GPU 日志。根因是 IAT Hook 安装晚于 Bond 的 D3D9 Device 创建，属于 0.1 起潜伏的启动时序竞态。

- 英文 fallback 的运行时正文固定字段和最终原生字体选择仍需单独日志确认；本轮不扩大该算法。
- 战斗字幕仍封存，不进入本插件。
- 所有面向用户阅读的文档继续使用中文文件名。

## 1. 项目目标与不可变边界

目标是在不修改 `Bond.exe` 的前提下，以一个正常源码构建的 Win32 `BloodstoneCN.asi` + 外置 BFA/BLI/86 LOC 完成简体中文运行时整合。

当前技术目标：

> **86 个 LOC 中已经存在中文的任何可翻译游戏文本，都不应因为加载、上下文、模板、生命周期或渲染路径问题继续显示英语。**

必须遵守：

1. 不新增翻译正文；
2. 不修改现有 LOC 内容来迁就代码；
3. LOC 是唯一最终中文正文来源；
4. BLI3 只做 source/key/hash/context/defer/历史 fingerprint；
5. 禁止 FIRST candidate；
6. 禁止 C++ 硬编码中文翻译正文；
7. 不建立替代 LOC 的翻译 TSV/JSON；
8. `BloodstoneCN.asi` 自身保持单一主汉化 ASI；NPC 字幕是另一个可选、完全独立的 `NPCSubtitles.asi`，不再并入主插件；
9. 每个源码包/编译包都必须带本文件的完整更新版。

## 6. R10 生产架构

### 6.1 文本替换 Hook 仍只有两个

```text
GetText     0x00E87740
SubmitText  0x00E85900
```

R10 没有恢复 UIDialogue、TextPathProbe、Renderer probe、EndScene maintenance。

### 6.2 GetText：Source First / Hash Second

R9 最新实机证据：

```text
primary=0x033DAF32 secondary=0x24DE92C2 source=MP7
primary=0x033DAF32 secondary=0x24DE92C2 source=Silenced P99
```

同一 hash pair 可以代表不同 source。R7.2/R9 会先按 hash 选 MP7，再由 short-code guard 把 P99 错误拦回原文；这能防事故，但不是根解。

R10：

```text
native original source
       ↓
exact BLI source family
       ↓
family 内部再用 primary/secondary hash 消歧
       ↓
无 hash 命中时，只有 family 全部 current LOC + flags 一致才允许
       ↓
否则 NO_GUESS
```

因此 P99 source family 中不会出现 MP7 source candidate。

新日志：

```text
SOURCE_FIRST_HASH_DISAGREEMENT ... policy=SOURCE_IDENTITY_WINS
SOURCE_FIRST_HASH_DISAGREEMENT ... policy=SOURCE_FAMILY_UNIQUE_AGREEMENT
```

已退役：

```text
ProtectShortCodes
FindShortModelCode
LOC_SHORT_CODE_SOURCE
LOC_SHORT_CODE_GUARD
```

这不是“去掉保护”，而是把保护前移为正确身份模型。

### 6.3 SubmitText

顺序：

```text
1. precise/deferred original key context
2. deterministic coverage，最多 2 pass
3. process-lifetime stable replacement
4. original SubmitText
5. optional NPC overlay sink
```

不回到 precise，不做三轮 alternating fixed-point。

NPC overlay 使用 `SubmitRawOverlay()` 直接走原 trampoline，不重新进入 resolver。

### 6.4 Font Ready Gate

```text
BFA CPU loaded
→ D3D device
→ GPU atlas ready
→ NativeGlyph installed
→ localization output enabled
```

Reset 前关闭，atlas 重新建立后恢复。

## 8. NPC / 环境对白字幕主程序集成

### 8.1 历史原型结论

独立 N2/N3/N4 ASI 已证明：

```text
DIALOGUE.arg0
→ script_dialogue key_hash
→ loose LOC 中文
→ 可以显示
```

但独立 D3D9 renderer 存在：

- 标点 bearing/advance 不自然；
- 字形基线与主游戏不一致；
- 中文禁则/换行差；
- 底部与原生字幕/通信/提示冲突；
- 重复维护第二套字体与 renderer。

因此独立 ASI 路线只保留历史证据，不进入正式架构。

### 8.2 `NpcDialogueIndex`

运行时直接解析：

```text
BSCNContents\loc\**\*_script_dialogue.loc
```

不生成/依赖 `npc_subtitle_hashes.inc`。

默认分类：

```text
ON:  _CMxx_ _CWxx_ _BGxx_ CIVILIAN BARMAID BARMAN WAITER WORKER FOREMAN SCIENTIST
OFF: _PGxx_ GUARD DELTA BRAVO SQUAD TEAM RADIO
EXCLUDE: BOND NICOLE DANTE MON_DIA_ _TUTORIAL_ _INFO_ _CS_
```

相同 hash 若对应不同 key/text → 从 NPC index 中剔除，NO_GUESS。

### 8.3 `NpcSubtitleBridge`

只 Hook：

```text
0x0093A2A1
```

调用原函数后：

```text
lookup hash
→ dedupe
→ queue
```

同 hash 在 `DedupeMs` 内只刷新已有字幕。

### 8.4 显示链

```text
NpcSubtitleBridge queue
→ SubmitTextBridge overlay sink
→ raw original_submit_text_ trampoline
→ game UI renderer
→ NativeGlyph / fonts.bfa
```

禁止：

- 第二个 SubmitText hook；
- EndScene overlay；
- 独立字体 atlas；
- NPC 字幕再经过 TextCoverage；
- BattleChatter 代码进入主线。

### 8.5 当前 TopSafe 仍需实机校准

默认：

```ini
Placement=TopSafe
TopSafeY=0.22
MaxWidth=0.66
MaxVisibleLines=2
LogSubmitTextContext=1
```

R10 首版会输出最多 64 类 `NPC_SUBMIT_CONTEXT`。坐标/layer/height 当前只是保守估算，必须结合实机截图决定哪一类 context 最适合作为稳定 NPC UI 宿主。

### 8.6 降级安全

NPC 是附加模块。索引或 bridge 失败时记录：

```text
NPC_DIALOGUE_INDEX_DISABLED ... main_localization=CONTINUE
NPC_SUBTITLE_BRIDGE_DISABLED ... main_localization=CONTINUE
```

主中文链必须继续启动。

SubmitText 可能跨线程，因此 16ms overlay gate 使用原子 CAS，避免多线程同时间片重复提交。

## 10. 已确认成功方案

### 10.1 OLTX

格式已破解：

```text
Header
Language Directory: 8 × 24
Key Table: [count][stride=8][hash+rel_offset][ASCII data]
Language block: [count][stride=8][hash+rel_offset][UTF-16LE data]
```

`rel_offset` 相对各自 block 起点；语言块由目录给绝对 offset/size。

### 10.2 BFA / DXT1

BPR/BFA 的历史 DXT1 字节序等底层格式已解决；当前不再是阻塞。

### 10.3 AP1 / 动作 token

正确方式：完整识别 `~~{NAME}~~`，保留 token，只解析正文并重组。不能猜 `{}`/样式串。

已见 token 代表：

```text
ARROWLEFT ARROWRIGHT SPRNT FLOW WFKL WAIM WFIRE CTXMO PAUSE SKIP Y
ARROWDOWN ARROWUP CAPSLOCK RETURN TAB PHN PHNUS WRLD SPACE LSHIFT PGUP RS
```

### 10.4 Stable SubmitText buffer

替换文本进入 process-lifetime 节点式 map，避免 caller 异步持有局部 `wstring.c_str()`。

### 10.5 Canonical / collision guard

大小写、冒号空格、引号、dash、ellipsis、whitespace 可做技术 canonical，但 canonical 后出现不同 replacement 就删除该 alias，NO_GUESS。

## 11. 永久失败/禁止回退的路线

### 11.1 R5M9 全局 spacing Hook

导致灾难性排版，永久禁止四个地址。

### 11.2 T4 PE section / binary merge

曾导致 `0xc000007b`。禁止二进制拼接、section injection、自制 merged ASI。

### 11.3 T5 大类重构

产物约 280K，架构错误；废弃。

### 11.4 “resolver hit = 成功”

错误层级：

```text
resolver hit
≠ effective content 已变中文
≠ renderer 已消费
≠ 用户看见中文
```

R6 以后按 UTF-16 内容差异判定，不按指针不同判定。

### 11.5 BLI3 replacement 作为最终译文

R6 实机出现大量“只把逗号改成顿号”的伪中文，证明 BLI3 snapshot 会落后于当前 86 LOC。R7 起 LOC 权威，BLI 只做 fingerprint/context。

### 11.6 UIDialogue final-object 正式常驻

研究期证明 `self+0x20` 可写，但位置太晚、上下文已丢、直接修改长期对象，而且曾怀疑干扰实时过场；R9 起退出生产链。

### 11.7 TextPathProbe / Renderer probe 正式常驻

研究目标已完成，不能为了“看日志”常驻改写 direct calls / renderer slot。

### 11.8 任意 substring 翻译

曾造成长英语中只替换短词的污染。只允许结构化 boundary / template / token / speaker-body 规则。

### 11.9 R7.2 short-model guard 作为最终方案

它实机防住 P99→MP7，但 R9 日志证明 root cause 是 hash identity 本身不可靠。R10 已由 Source First / Hash Second 取代。

### 11.10 R9 broad dialogue auto-defer 作为 CG 修复

预渲染 CG 实机仍快。普通 speaker/body defer 不再作为 CG 修复路线。

### 11.11 独立 NPC D3D9 renderer 正式化

N3/N4 可显示，但排版/标点/风格/位置维护成本高。R10 只保留其事件入口经验，显示迁入主 SubmitText。

## 18. R10.1 NPCIndexRepair 实机故障闭环

### 18.1 用户实机结果

用户只检查了 NPC 字幕，结果是：**完全没有 NPC 字幕**。本轮未检查 P99/MP7 与 CG，因此这两个方向不得凭空改动。

R10 日志给出决定性证据：

```text
NPC_DIALOGUE_INDEX_READY files=0/23 parsed=0 accepted=0 records=0 ambiguous_hashes=0 source=BSCNContents\loc
NPC_DIALOGUE_INDEX_DISABLED reason=INITIALIZE_FAILED main_localization=CONTINUE
NPC_SUBTITLE_MODE enabled=0 renderer=GAME_SUBMITTEXT battle=SEALED index_records=0
```

解释：

1. `CollectLocFiles` 已找到 23 个 `*_script_dialogue.loc`，运行目录正确；
2. 23 个文件没有任何一个通过 parser；
3. `NpcDialogueIndex::Initialize` 返回 false；
4. NPC bridge 被禁用；
5. `0x0093A2A1` hook / raw SubmitText / TopSafe 坐标都还不是当前故障层。

### 18.2 R10 parser 根因

R10 直接使用：

```cpp
const uint32_t key_block = U32(file.data() + 0x18);
```

历史已验证 OLTX 样本却是：

```text
header+0x08 = 0x10
header+0x18 = 0xCC
Language Directory = 0x1C..0xDB
Key Table actual = 0xDC
```

因此 `0x18` 不是可以无条件按绝对 Key Table offset 使用的字段。`0xCC` 会落到 Language Directory 内部。

### 18.3 R10.1 修复方案

`src/npc_dialogue_index.cpp` 改成验证式发现：

```text
HEADER_ABSOLUTE
HEADER_PLUS_BASE = header[0x18] + header[0x08]
DIRECTORY_END    = 0x1C + 8*24
VALIDATED_SCAN   = directory_end..first_lang_block，4-byte aligned
```

候选必须全部通过：

- count 合法；
- stride == 8；
- table 不越过第一个语言块；
- 每个 key rel offset 指向 key data；
- key 为非空可打印 ASCII + NUL；
- 至少一个 key hash 与目标语言块相交。

历史 `0xCC + 0x10 = 0xDC` 样本由 `HEADER_PLUS_BASE` 恢复；`DIRECTORY_END` 同样给出 0xDC。

### 18.4 Partial parse

单个脚本文件坏掉不再直接拖垮全部 NPC 字幕：

```text
坏文件 -> NPC_LOC_PARSE_FAIL -> NO_GUESS / 不产生 record
好文件 -> NPC_LOC_PARSE_OK   -> 保留 record
至少一个好文件 + records>0 -> NPC 模块继续
```

若只有部分成功：

```text
NPC_DIALOGUE_INDEX_PARTIAL ... action=KEEP_VALID_RECORDS
```

这不是 first-candidate fallback；坏文件的数据完全不使用。

### 18.5 下一轮日志层级

必须按顺序：

```text
NPC_LOC_KEY_TABLE_RECOVERED / NPC_LOC_PARSE_OK
        ↓
NPC_DIALOGUE_INDEX_READY records>0
        ↓
NPC_SUBTITLE_BRIDGE_PREPARED
        ↓
NPC_DIALOGUE_HOOK_OK
        ↓
NPC_SUBTITLE_HIT
        ↓
NPC_SUBMIT_CONTEXT
        ↓
用户可见字幕
```

**只有出现 `NPC_SUBTITLE_HIT` 而画面仍无字幕，才允许继续调查 raw SubmitText context/layer/position。**

## 23. R10.2 native SubmitText overlay 的三个结构性错误

### 23.1 “本时间片第一个 SubmitText context”不是安全 anchor

R10.2 在每个约 16ms slice 中只允许一次 overlay，但它不是选择最佳 native context，而是当前哪个 SubmitText 回调先到就直接复用。

NPC 活动期间记录到的实际 context 包括：

```text
pos=(2.200,50.000,0.000)   height=16 width=0 layer=4
pos=(12.000,-4.000,0.000)  height=14 width=0 layer=6
pos=(0.000,-22.000,0.000)  height=16 width=0 layer=4
pos=(0.000,-100.000,0.000) height=18 width=0 layer=4
```

`width=0` + 小型局部坐标非常像子 HUD/UI element。它们可以作为游戏自己的文字提交参数，但没有证据能作为“创建一个新的、全屏定位的 NPC 字幕”的 anchor。

R10.2 的 16ms gate 反而让这些早到的局部 context 把后面更好的 screen-space context 挡掉。

### 23.2 1280×720 虚拟 UI 假设没有实机依据

R10.1 更完整的 context 诊断已经出现：

```text
pos=(320.000,360.000,0.000) height=20 width=512 layer=4
pos=(320.000,365.000,0.000) height=20 width=550 layer=4
```

还出现 y 接近 444 的 UI 坐标。

这些参数更符合 **640×480 虚拟 UI**：

- x=320 正好为水平中心；
- width=512/550 是合理的大型文本框宽度；
- y=360/365/444 都落在 480 高画布内。

R10/R10.2 却把 TopSafe 按 1280×720 算为：

```text
x = 640
width = 1280*0.66 = 844.8
```

若真实虚拟画布为 640 宽，则 x=640 已在最右边界，足以导致完全不可见。

这里“640×480”仍是**基于参数分布的最强当前推断**，不是已经逆出硬编码画布常量。R10.3 必须继续用日志验证。

### 23.3 SubmitText position ABI 至少按四 float 观察

历史 SubmitText 参数内存快照曾记录 position 指针指向：

```text
[x, y, 0.0f, 0.0f]
```

即 4 个连续 float。

R10.2 自己构造 overlay position 时却使用：

```cpp
float position[3];
```

如果原游戏 SubmitText 在任何路径读取第四分量，R10.2 就会越过本地数组读相邻栈内容。R10.3 必须使用 4-float position buffer。

### 24.4 screen-space anchor 评分

硬条件：

```text
manager/position/vertex_colors/style 非空
position 4 float 可读
10 <= height <= 64
160 <= width <= 900
abs(x),abs(y) <= 2048
abs(z) <= 1
```

`width==0` 直接排除。

加分：

```text
x in 280..360        +5
y in 280..430        +4
height in 18..24     +3
layer == 4           +2
context_ac == 0      +2
context_a8 in 1/2    +1
```

基础分 8，只有：

```text
score >= 18
```

才成为 anchor。

这会优先捕获 R10.1 已见的 `(320,360/365,width=512/550,height=20)` 类 context，而拒绝大多数局部 HUD 调用。

### 已验证历史

N3 独立 ASI 曾由用户实机确认：普通 NPC/场景对白能够显示中文字幕。其核心链路已经成立：

  ↓

### 当前 0.1 实现

- 复用 R10.3 已修好的 OLTX `*_script_dialogue.loc` 解析器。
- 支持 key table 三种格式推导和 `VALIDATED_SCAN` fallback，保留 `0xCC + 0x10 = 0xDC` 的历史坑修复。
- 相同 hash 对应不同 key/text 时剔除，继续 `NO_GUESS`。
- 默认 `CoverageFirst=1`：除明确 hard-exclude 外优先显示 script_dialogue，避免旧 674 whitelist 长期失同步。

## C. 英文原生 fallback

这是本版新路线。目标是即使完全没有 BloodstoneCN 资源，原版英文游戏也能得到 NPC 字幕。

### 文本来源

禁止内置 674 条英文句子。0.1 在调用原始 `0x00F12820(dialogue_id)` 后，对其**返回对象**做安全只读探测：

1. 当前对象前 384 bytes；
2. 内联 ASCII / UTF-16；
3. 32 位指针字段指向的一级对象/字符串；
4. 对候选进行“自然英文对白”评分；
5. 同时尝试识别 `Monaco_01_CW01_199` 这类 key 名。

所有读取使用 `ReadProcessMemory`，无效指针只产生 MISS，不直接解引用崩溃。

若 key 能识别，则仍应用 hard-exclude；若 key 无法识别，默认 `AllowUnknownDialogue=1` 以优先实现英文版 NPC 字幕覆盖。这个策略需要实机日志后继续收紧。

### 游戏原生英文字体

英文模式不加载 Windows 字体，也不使用 BFA。它只在英文 fallback 模式 Hook：

```text
Native glyph lookup slot  0x011A02D8
Resource resolve CALL      0x00E42C21
font resource handle       font + 0x12C
resource texture pointer   resource + 0x08
```

捕获游戏实际使用的 font、variant、scale、resource handle 与 D3D9 texture；绘制英文字符时再次调用链中的原始 glyph lookup 获得 UV/advance，并使用游戏自己的纹理。

这避免了“英文版仍要求中文 BFA”的错误依赖。

### 当前未知项

0.1 尚未实机证明：

- `0x00F12820` 返回对象能否稳定找到完整英文正文；
- 一级指针探测是否已经覆盖所有关卡对象结构；
- 最近一次 NativeGlyph font 是否就是适合 NPC 字幕的原生 UI 字体；
- 原生 glyph 自绘的基线/字距是否需要进一步校准。

因此英文 fallback 当前属于**功能验证阶段**，不是“已经完成”。

## D. D3D9 共存策略

- Hook Bond.exe 的 `Direct3DCreate9` IAT，但采用 chain 模式：保留当时槽位已有函数作为 previous。
- Hook `IDirect3D9::CreateDevice` vtable slot 16，并继续 chain。
- Hook `IDirect3DDevice9::EndScene` vtable slot 42，并继续 chain。
- **0.1 不 Hook Reset。** 中文 BFA 使用 `D3DPOOL_MANAGED`；去掉第二个 Reset hook 可降低与 R10.4 主汉化/其它 wrapper 的冲突。
- R10.4 主汉化当前没有 EndScene hook，因此两者职责边界清晰。

# NPCSubtitles 0.2.1 D3D9Bootstrap 新增接档

## H. 0.1 最新实机结论

2026-08-10 用户对 `NPCSubtitles 0.1 AutoFallback` 实机反馈：

> “效果超出预期，非常棒”

这确认了当前独立插件的核心路线已经成立：NPC Dialogue 捕获后通过独立 D3D9 自绘可以稳定生成可见字幕，不需要重新回到游戏 `SubmitText 0x00E85900` 创建 UI。

同时确认三个问题：

1. 自动换成双行时，两行间距明显过大；
2. 字幕相对位置仍略低；
3. **改变游戏分辨率后，NPC 字幕不再显示。**

第 3 项是 0.2 的最高优先级阻塞 Bug。

## I. 分辨率 Bug 的 0.2 处理

### 0.1 的设计缺口

0.1 明确没有 Hook `IDirect3DDevice9::Reset`，理由是中文 BFA 使用 `D3DPOOL_MANAGED`，希望尽量减少与 BloodstoneCN / wrapper 的 Hook 面。

实机结果已经证明：

> “不 Hook Reset”不能继续作为正式策略。

即使 `D3DPOOL_MANAGED` 理论上可跨普通 Reset 保持资源，NPCSubtitles 还同时依赖 device/viewport、EndScene 生命周期以及英文 fallback 捕获到的游戏原生纹理裸指针；因此分辨率变化必须被当作显式 D3D9 生命周期事件处理。

### 0.2 新 Hook

```text
Bond.exe Direct3DCreate9 IAT
  ↓
IDirect3D9::CreateDevice [16]
  ↓
IDirect3DDevice9::Reset [16]      NEW
IDirect3DDevice9::EndScene [42]
```

Reset 继续使用 chain：安装时保存 observed previous function；`HookReset` 先做 NPCSubtitles 自己的资源失效，再调用 previous Reset，成功后完成重建。

### 中文 BFA

Reset 前：

```text
FontAtlas::InvalidateGpuTexture()
```

仅释放 GPU texture/device 绑定，CPU 侧 BFA 像素、glyph 表、line height 等全部保留。

Reset 成功后：

```text
FontAtlas::EnsureTexture(device)
```

立即重新创建并上传 BFA atlas。

新增日志：

```text
NPC_SUBTITLE_RESET_HOOK_OK
NPC_SUBTITLE_DEVICE_RESET_BEGIN request=<w>x<h> windowed=<0|1>
NPC_SUBTITLE_DEVICE_RESET_FAILED hr=0x........
NPC_SUBTITLE_DEVICE_RESET_OK mode=CHINESE_BSCN chinese_texture=1 viewport=<w>x<h>
NPC_SUBTITLE_POST_RESET_DRAW_OK viewport=<w>x<h>
```

### 英文 fallback

英文模式捕获的 `resource + 0x08 -> IDirect3DTexture9*` 是游戏拥有的裸指针。Reset 后继续使用旧指针有失效风险，因此 0.2 在 Reset 前：

```text
NativeFontCapture::InvalidateGpuResources()
```

清空 texture cache，但保留 font candidate / glyph hook / resource hook。之后由游戏正常字体路径重新经过 resource resolve Hook 时捕获新纹理。

本轮**不主动调用游戏内部 resource resolver 来强行重建**，因为那会引入新的线程/生命周期假设，超出解决当前 Bug 所需范围。

## J. 0.2 布局调整

默认：

```ini
[Display]
Scale=0.56
BaseY=0.120
MaxWidth=0.66
LineSpacing=0.82
MaxVisibleLines=3
```

相对 0.1：

```text
BaseY 0.145 → 0.120
```

在 720p 基准下约向上移动 18 像素，并继续按 viewport 高度等比缩放。

双行不再只依赖完整 atlas line height。现在使用：

```text
nominal = line_height * scale * LineSpacing
minimum = 上一行实际可见 glyph 高度 + 约 1 个 720p 基准像素
advance = max(nominal, minimum)
```

因此可以明显收紧行距，又不会因为用户把 `LineSpacing` 调小就直接压字重叠。英文模式采用同样的“实际 glyph 高度下限”原则。

并发字幕事件之间的垂直步进也从 0.1 的：

```text
block * 1.55
```

收紧为：

```text
block * 1.30
```

# 0.2.1 D3D9Bootstrap 最新接档补充（2026-08-10）

## 用户实机反馈

0.1：字幕显示成功，效果超出预期；双行间距偏大、位置略低；改变分辨率后字幕消失。

0.2 ResetLifecycle：首次启动后字幕完全不显示。用户提交日志中：

```text
RESOURCE_MODE ... selected=CHINESE_BSCN
NPC_DIALOGUE_INDEX_READY files=21/22 ... records=1314
NPC_SUBTITLE_D3D9_IAT_HOOK_OK
NPC_DIALOGUE_HOOK_OK
NPC_DIALOGUE_EVENT ... index=HIT allowed=1
NPC_SUBTITLE_QUEUE ...
```

而以下日志全部缺失：

```text
NPC_SUBTITLE_CREATE_DEVICE_HOOK_OK
NPC_SUBTITLE_RESET_HOOK_OK
NPC_SUBTITLE_ENDSCENE_HOOK_OK
BFA_GPU_OK
```

因此直接否定“LOC/Dialogue/queue 导致不可见”，故障点确定为 D3D9 Device/EndScene Hook 没有建立。

## 0.2.1 根因与修复

插件 Worker 会先完成 BFA/LOC/index 初始化，再调用 `g_renderer.Install()`。该次实机日志从 18:49:29.296 启动到 18:49:29.760 安装 D3D9 IAT Hook，相差约 464 ms。Bond 很可能已经完成 `Direct3DCreate9/CreateDevice`，后装 IAT 无法回溯已发生调用。

0.2.1 保留 IAT Hook，并在安装后立即调用 `BootstrapDeviceHooks()`：

1. 用 observed previous `Direct3DCreate9` 建临时 IDirect3D9；
2. chain Hook `IDirect3D9::CreateDevice [16]`；
3. 创建隐藏 8x8 HAL Device；
4. 从 Device vtable chain Hook `Reset [16]`、`EndScene [42]`；
5. 临时 Device 不初始化字幕 GPU 资源；
6. 释放临时 Device；
7. 首次真实 EndScene 记录 `NPC_SUBTITLE_ENDSCENE_ACTIVE`。

这使插件不再依赖“ASI 是否恰好早于游戏 D3D9 初始化”这一非确定时序。

## 0.2.1 首轮测试判定

理想启动日志：

```text

NPC_SUBTITLE_D3D9_BOOTSTRAP_BEGIN

NPC_SUBTITLE_RESET_HOOK_OK
NPC_SUBTITLE_ENDSCENE_HOOK_OK
NPC_SUBTITLE_D3D9_BOOTSTRAP_OK device_type=HAL reset=1 endscene=1
NPC_SUBTITLE_ENDSCENE_ACTIVE viewport=<真实分辨率>
```

随后触发中文 NPC：

```text

NPC_DIALOGUE_EVENT ... index=HIT allowed=1
NPC_SUBTITLE_QUEUE ...
```

若上述成立且字幕恢复，再继续验证 720p→1080p→720p 等分辨率 Reset 生命周期。

## 不相关但保留的现象

# NPCSubtitles 0.2.2 D3D9InteropSafe 最新完整接档补充（2026-08-11）

## 1. 0.2.1 实机结果：NPC bootstrap 破坏了 BloodstoneCN 主汉化

用户截图表现：版权页原本正常的中文/英文版权文字被大量碎裂字形、错贴纹理覆盖，主汉化显示明显异常。

两份同次运行日志给出确定时间关联：

```text
NPCSubtitles 0.2.1
01:41:46.730 NPC_SUBTITLE_D3D9_IAT_HOOK_OK
01:41:46.738 NPC_SUBTITLE_D3D9_BOOTSTRAP_BEGIN
01:41:46.814 NPC_SUBTITLE_CREATE_DEVICE_HOOK_OK source=bootstrap
01:41:47.444 NPC_SUBTITLE_RESET_HOOK_OK
01:41:47.458 NPC_SUBTITLE_ENDSCENE_HOOK_OK
01:41:47.465 NPC_SUBTITLE_D3D9_BOOTSTRAP_OK
```

同一时刻 BloodstoneCN：

```text
01:41:46.589 Direct3DCreate9 IAT hook installed
01:41:46.814 D3D9 CreateDevice hook installed
01:41:47.444 BFA_GPU_OK texture=07E13340
01:41:47.444 FONT_GATE_READY localization_output=ENABLED
```

尤其是 `01:41:46.814` 使用了与 NPC worker 相同的线程上下文，证明 BloodstoneCN 的 `D3D9 CreateDevice hook installed` 是由 NPCSubtitles 的 bootstrap 调用链触发，而不是 Bond 正常渲染线程独立触发。

## 2. 确认根因

0.2.1 的 bootstrap 是：

```text
NPC previous_d3d9_
  ↓
HookD3D9(dummy IDirect3D9)
  ↓
NPC previous_create_
  ↓
创建 8x8 HAL dummy Device
```

这里的 `previous_*` 是“链中的前一个函数”，不等于“微软 D3D9 原函数”。

当 BloodstoneCN 已经抢先安装 `Direct3DCreate9` IAT Hook 后：

```text
NPC previous_d3d9_ == BloodstoneCN 的 Direct3DCreate9 Hook
```

NPC 调用它创建临时 D3D9 对象，等于主动进入 BloodstoneCN 的 D3D9 Hook。随后 NPC 的 8×8 dummy Device 又经过 BloodstoneCN 的 CreateDevice 路径。

结果 BloodstoneCN 误把 dummy Device 当成 Bond 真正游戏 Device，并在其上执行：

```text
BFA_GPU_OK
FONT_GATE_READY
```

这解释了版权页纹理严重错乱。

**结论：0.2.1 bootstrap 架构不允许继续使用。**

## 3. 0.2.2 修复架构

### 3.1 D3D9 Hook 提前

0.1/0.2 的真实缺口仍然存在：Renderer 原来是在 22 个 NPC LOC 全量解析之后才安装，可能晚于 Bond 创建 Device。

0.2.2 改为：

```text
LoadConfig / Validate Bond
  ↓
DecideResources
  ↓
只加载 Chinese BFA CPU atlas（很快）/ 或 Prepare native font
  ↓
立即 Prepare + Install NPC Renderer
  ↓
再做 22 个 NPC LOC DialogueIndex 扫描
  ↓
最后安装 Dialogue Hook
```

因此正常路径不再需要依靠 late bootstrap 才赶上 D3D9。

### 3.2 bootstrap 不再经过任何 previous chain

新路径：

```text
GetModuleHandleW("d3d9.dll")
  ↓
GetProcAddress("Direct3DCreate9")
  ↓
直接调用 d3d9.dll export
```

这绕过 Bond.exe 的 `Direct3DCreate9` IAT，因此不会调用 BloodstoneCN/NPCSubtitles 的 IAT chain。

### 3.3 不再 Hook dummy IDirect3D9::CreateDevice

0.2.1 的：

```text
HookD3D9(d3d, "bootstrap")
previous_create_(...)
```

全部废除。

0.2.2 只读取 raw `IDirect3D9` 的 `vtable[16]`，确认它仍属于 `d3d9.dll` 后直接调用一次原生 CreateDevice。

### 3.4 Foreign CreateDevice 安全闸

如果 `vtable[16]` 已经指向其它模块：

```text
NPC_SUBTITLE_D3D9_BOOTSTRAP_SKIP_FOREIGN_CREATEDEVICE
```

立即放弃 dummy Device。此时宁可只保留 IAT future-call 路线，也绝不再穿过其它 ASI 的 CreateDevice Hook。

### 3.5 dummy Device 只用于共享 Device vtable

如果 raw CreateDevice 安全：

```text
8×8 dummy IDirect3DDevice9
  ↓
只补装 Reset [16]
只补装 EndScene [42]
  ↓
Release dummy
```

不会用 dummy 建立 NPC BFA GPU texture；更不会让 BloodstoneCN 看见它。
