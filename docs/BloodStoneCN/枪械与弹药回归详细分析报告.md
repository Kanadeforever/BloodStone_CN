# 007 Blood Stone 汉化 — R10.4 枪械/弹药与 W1 字体时序回归详细分析报告

> 更新：2026-08-16  
> 当前候选：R10.4 W1.1 WeaponHudLifecycle + FontGateEarlyD3D  
> 基线原则：R10.4 已有中文覆盖不可回退；W1/W1.1 只验证武器 HUD 生命周期与字体时序。

## A. W1 实机新增结论：中文口口口与枪械实验无直接关系

W1 最新实机日志中，`fonts.bfa` 的 CPU 解析成功，但完整 GPU 链没有建立。关键时序为：

```text
23:58:12.130 BFA_CPU_OK
23:58:13.326 FONT_GATE_WAIT ... ATLAS_NOT_READY
23:58:13.326 Direct3DCreate9 IAT hook installed
23:58:13.326 NATIVE_GLYPH_HOOK_OK
23:58:13.326 Initialization ... font_render_ready=0
```

此后直到日志结束均没有：

```text
D3D9 CreateDevice hook installed
BFA_GPU_OK
FONT_GATE_READY
```

而十秒后却出现：

```text
FONT_GATE_SKIP_GETTEXT action=KEEP_ORIGINAL
TEXT_COVERAGE_HIT mode=exact
HUD_SUBMIT_TRACE ... translated=1 ... effective=血石 © 2010 ...
```

这证明 R10.4/W1 的门禁存在不对称：GetText 知道字体未 ready，SubmitText 却仍可通过 TextCoverage 产出中文。实际画面上的方框因此不是缺字，而是中文进入了原生字体路径。

历史可用 R10.4 test1e 对照则是：IAT 约在启动后 0.126 秒安装，之后成功捕获 CreateDevice，并出现 `BFA_GPU_OK` 与 `FONT_GATE_READY`。W1 本轮 IAT 安装约在 BFA CPU 完成后 1.196 秒；究竟为何本次 LOC/BLI 首次读取耗时更大，还不能仅凭一份日志归因，但 **D3D Hook 不应依赖文本索引速度**，因此 W1.1 将图形 Hook 无条件前移。

这项修复与武器/弹药根因实验正交：没有改变 R10.4 的翻译候选、TextCoverage 内容或 W1 的 source/hash 生命周期实验。

## 1. 执行摘要

当前枪械问题不应再简单归类为“P99/MP7 翻译选错”。现有 R10.4 实机日志已经证明，在 `Silenced P99` 这个关键复现点上，R10.4 的 **Source First / Hash Second** 确实选到了正确的中文 `消音P99`；然而随后画面仍可能出现武器名切换错乱，同时弹药计数出现不随射击/换枪正确更新的现象。

综合 R7.1→R7.2→R8→R9→R10→R10.4 的代码演变，最符合全部证据的解释是：

1. **R7.1 的确存在“stale hash 把 P99 当 MP7”的身份选择 bug**；
2. R7.2/R8 已经通过“保留游戏原始 source/指针，再在更晚的 SubmitText 做中文化”的工作方式实机修复过这类武器 HUD；
3. R10 将身份选择升级为 Source First / Hash Second，正确解决了“hash 不能定义文本身份”的问题，但同时让大量静态文本更早在 GetText 阶段直接返回插件 LOC 的常驻 `wchar_t*`；
4. 对 `UIWeaponPanel` 这一类会复用对象、更新内部文本缓冲/指针的 HUD，这个“**正确中文，但过早替换为插件常驻指针**”很可能破坏了游戏原本依赖的生命周期/缓存语义；
5. 弹药计数属于更强的动态数据，任何进入 LOC、TextCoverage 或 process-lifetime stable string 的行为都不合适，应当保持 game-owned mutable buffer 从 GetText 到 SubmitText 全程原样流动。

因此 W1 **不回滚 R10.4 的 Source First / Hash Second，不恢复 R7.2 的全局 KEEP_ORIGINAL，不削减 TextCoverage，也不允许已有中文回退英文**。它只做两种非常窄的“交付时机”修正：

- 纯动态数值 HUD：永远使用游戏自己的可变指针，跳过翻译/稳定池；
- `native source` 已正确识别、但 runtime hash 明确 stale，且文本含技术身份 token（如 `P99` / `A.R.`）时：GetText 保留游戏原指针；已经选中的现有 LOC 中文不丢弃，而是沿用 R10.4 已有 precise/deferred 上下文，在 SubmitText 才注入。

这是一版**生命周期修复验证版**，不是新翻译器。

## 2. 已确认事实、强假设与未证明项

### 2.1 已确认事实

- Bond.exe 是 Win32 PE32/i386；当前已知版本 ImageBase `0x00400000`，timestamp `0x4CA36144`，image size `0x010CC000`。
- 已验证文本入口：
  - GetText `0x00E87740`
  - GetText slots `0x01179FC0 / 0x0117A690 / 0x0117A7D8`
  - SubmitText `0x00E85900`
- GetText 对象 `self+0x194 / self+0x190` 的 hash 字段存在缓存/复用，不能作为文本身份。
- R7.1 曾实机出现 P99 HUD 显示为 MP7。
- R7.2/R8 曾实机修复 P99/MP7 串线。
- R8 实机日志证明同一组 runtime hash 可以先对应 `MP7`，后又对应 `Silenced P99`。
- R10.4 当前实机日志在 `Silenced P99` 处记录了 `SOURCE_FIRST_HASH_DISAGREEMENT`，随后能得到 `消音P99`，说明 Source First 的候选选择在该点是正确的。
- R10.4 CoreCleanup 本身主要删除 NPC 集成；`external_loc.cpp`、`loc_text_bridge.cpp`、`text_coverage_resolver.cpp` 等核心文本文件并非在 CoreCleanup 这次提交才引入身份模型变化。因此当前回归更可能是 **R10 系列继承行为**，而不是“删除 NPC 代码”直接造成。
- R5/R6 已经证明“指针变了”不能作为文本真正变化的判据；后续日志必须按 UTF-16 内容判断 translated 状态。

### 2.2 强假设

- 武器名错乱的主要剩余问题已从“选错翻译”转移为 **UIWeaponPanel / GetText 返回指针生命周期和缓存语义**。
- 弹药冻结/不更新属于同一大类“动态 HUD 不应被稳定化”，但不保证与武器名完全是同一个内部字段或同一对象。

### 2.3 尚未证明

- 尚未通过 W1 实机日志证明同一个 `self` 在换枪时发生 `Silenced P99 -> MP7 -> ...` 的 source transition。
- 尚未证明原版 UIWeaponPanel 是否直接比较 `wchar_t*` 地址、缓存 GetText 指针，还是把其指针保存在另一层对象中。
- 尚未证明弹药最终只经过已知 GetText/SubmitText；若 W1 的动态 scalar trace 完全抓不到弹药，则必须继续逆 `UIWeaponPanel.cpp` 的数值更新路径，而不能扩大翻译规则。

## 3. 版本考古：问题究竟从哪里出现

### 3.1 R2 / R3：基础链稳定，R3 恢复完整 LOC Loader

R2 已经有可启动、字体/M2F1 基础正常的单 ASI。R3 恢复了 86 个 loose LOC Loader。此时核心关注还是“让已有 LOC 中文进入游戏”。

### 3.2 R4～R6：解决覆盖和最终消费，但暴露“指针 != 内容”陷阱

R4/R5 增加了更多最终文本覆盖、SubmitText 稳定字符串和研究性后置路径。R5 的日志一度把 `source pointer != effective pointer` 视为 translated，实机却证明画面仍可保持英语。R6 因此明确改成按 UTF-16 内容差异判断。

这段历史非常重要：它说明 **Bond 的文本链对指针/对象生命周期敏感，不能只看字符串内容或“resolver 命中”**。

### 3.3 R7.1：第一次明确出现 P99 → MP7

R7.1 的 `SelectCandidate()` 在 hash 只有一个 BLI 候选时直接信任 hash。实际 HUD 中 hash 字段会复用，于是出现：

```text
当前对象 native source = P99 / Silenced P99
runtime hash             = 仍指向 MP7 语境
旧选择器                 = 认为唯一 hash 就是正确身份
结果                     = P99 被映射成 MP7
```

这是**已确认的旧根因**。

### 3.4 R7.2：旧问题的第一版有效修复

R7.2 增加两层保护：

1. 即使 hash 候选唯一，只要 native GetText source 存在，就必须校验 source；不一致则 KEEP_ORIGINAL；
2. 再做通用短型号守恒：P99/MP7/M16/AK47 这类字母数字身份必须在 replacement 中保持，否则 KEEP_ORIGINAL。

关键不是“黑名单保护”，而是其运行效果：**当 hash 不可信时，让游戏自己的 source 继续向后走**。

### 3.5 R8：最关键的已成功实机证据

R8 日志曾出现：

```text
primary=0x033DAF32 secondary=0x24DE92C2 source=MP7
primary=0x033DAF32 secondary=0x24DE92C2 source=Silenced P99
LOC_SHORT_CODE_GUARD source=Silenced P99 candidate=MP7 code=P99 action=KEEP_ORIGINAL
TEXT_COVERAGE_HIT mode=exact ...
TEXT_COVERAGE_MISS ... preview=消音P99
```

这组证据的含义是：

- runtime hash pair 确实不是身份；
- R7.2 guard 没有在 GetText 返回错误 MP7；
- 游戏自己的 `Silenced P99` 继续进入后续链；
- TextCoverage 在最终阶段仍能把它变成 `消音P99`；
- 历史接档明确记录用户当时确认 P99/MP7 串线已经修复。

因此，“**保留 game-owned source 生命周期 + 晚一点中文化**”是我们手里已有实机先例的方案。

### 3.6 R9：清理研究性 Hook，但不是一个可以盲目回滚的答案

R9 收敛成 GetText + SubmitText，删除 UIDialogue/TextPathProbe/EndScene 等研究性常驻 Hook。它仍继承 R7.2 的 source/hash 一致性与 short-code guard。

因此用户怀疑“R9 可能已经有问题”是合理的：R9 不是一个经过当前全部武器/弹药回归矩阵证明的黄金基线。我们不能简单用 R9 替换 R10.4；更不能为了武器回到 R9 而失去 R10.4 后来已经修好的中文覆盖。

### 3.7 R10：身份模型正确升级，但交付方式发生结构变化

R10 正式废弃 short-code guard，改为：

```text
native original source
    -> exact BLI source family
    -> primary/secondary hash 只在这个 source family 内消歧
    -> hash 无法消歧时，只在同 family 的 current LOC + flags 可安全一致时选
    -> 否则 NO_GUESS
```

这个身份模型是正确方向，W1 **完全保留**。

但 R10 常规静态命中会更积极地在 GetText 直接返回 `authoritative LOC std::wstring::c_str()`。对普通菜单/城市/任务这非常有效，也正是 R10.4 中文覆盖不能回退的原因；对会复用的武器 HUD，则可能把一个“游戏可变/可替换指针”提前换成“插件进程期常驻指针”。

### 3.8 R10.4：当前日志已经把“候选选错”与“画面错乱”分开

当前实际日志有：

```text
SOURCE_FIRST_HASH_DISAGREEMENT ... original=Silenced P99 ... policy=SOURCE_IDENTITY_WINS
TEXT_COVERAGE_MISS ... preview=消音P99
...
TEXT_COVERAGE_MISS ... preview=MP7
...
按住 ~~{WRLD}~~ 拾取 消音P99
```

因此至少在第一处 P99：

> R10.4 知道它是 `Silenced P99`，也能找到 `消音P99`。

如果画面随后仍变成 MP7，就不能继续把主要精力放在“再写一套 P99/MP7 选择规则”上。更值得验证的是：**哪个 HUD 对象/指针在换枪时被缓存了，插件到底给游戏返回了 GAME pointer 还是 PLUGIN pointer。**

## 4. 为什么不能全局回滚 R7.2 的 KEEP_ORIGINAL

当前 R10.4 日志里，以下完全正常、应该中文化的内容同样会出现 `SOURCE_FIRST_HASH_DISAGREEMENT`：

```text
Athens
Istanbul
Monaco
Siberia
Bangkok
Burma
Field Operative
Agent
Recruit
Mission Failed
Loading / Loading. / Loading.. / Loading...
ACCESS DENIED / ACCESS GRANTED
...
```

如果简单恢复：

```text
hash disagreement -> KEEP_ORIGINAL
```

这些已经正常中文化的项目会大面积重新显示英语。这直接违反当前最高约束：**R10.4 已可靠中文覆盖不得回归。**

所以 W1 的规则必须同时满足：

- source-first 候选选择保持不变；
- 非 HUD 技术身份文本完全不受影响；
- 即使技术身份 HUD 延迟，已选中的中文也必须在 SubmitText 注入，而不是放弃中文。

## 5. W1 修复设计

### 5.1 A 类：纯动态标量

识别范围故意很窄：

```text
10
9
10/30
100%
01:23
[7]
10|30
-1
```

只允许数字、空白和有限的 `+-.,/:%()[]|`。只要出现字母或 CJK，就不属于动态 scalar：

```text
P99           -> 否
MP7           -> 否
G36C          -> 否
Ammo 10       -> 否
Silenced P99  -> 否
Focus Aim     -> 否
49m           -> 否
```

处理：

```text
GetText      : 保留游戏原指针
TextCoverage : 直接跳过
SubmitText   : 原指针直通
stable pool  : 跳过
```

目的：弹药、计数、百分比、计时等由游戏每帧/每事件更新的缓冲永远不被 LOC/stable-map 固化。

### 5.2 B 类：source-first + stale hash + 技术身份标签

只在同时满足下列条件时改变交付时机：

1. R10 Source First 已经选到 exact native source family；
2. 当前 runtime primary/secondary 至少一个非零；
3. 所选 BLI record key_hash 与两个 runtime hash 都不一致，明确属于 stale-hash 场景；
4. native source 含通用技术身份 token，例如字母+数字，或 `A.R.` 形态；
5. authoritative LOC replacement 保留同一技术身份；
6. source 不是纯 `P99`/`MP7` 这种无自然语言前缀的纯身份标签。

处理：

```text
Source First 仍选中同一中文候选
        ↓
RememberPreciseMapping(candidate)
        ↓
GetText 不返回插件 LOC 指针
        ↓
继续返回 game-owned native source pointer
        ↓
在已有 DeferredContext / global deferred 保存“原 source + 已选中文”
        ↓
SubmitText 按 exact context 注入现有 LOC 中文
```

这不是“保持英文”。它只是把：

```text
GetText 时中文化
```

改为：

```text
SubmitText 时中文化
```

最终中文内容仍来自同一个 LOC。

### 5.3 C 类：普通 source/hash 正常文本

完全保持 R10.4 原行为。

### 5.4 D 类：城市、任务、菜单等非技术身份 stale-hash 文本

完全保持 R10.4 原行为。即使其 hash disagreement，也不会触发 W1 技术身份 defer，因此不会因为武器修复而重新出现英文。

### 5.5 内容相同的零差异候选

如果 authoritative 内容与 original 完全一致，例如：

```text
MP7 -> MP7
```

W1 不再把游戏原 pointer 替换成一个内容相同的 LOC pointer。既然画面没有任何变化，就没有理由承担一次指针所有权改变。

## 6. 新增诊断与如何判读

### 6.1 GetText HUD 追踪

```text
HUD_GETTEXT_TRACE self=... original_ptr=... returned_ptr=...
                  primary=... secondary=...
                  kind=DYNAMIC_SCALAR/TECHNICAL_IDENTITY
                  source=...
                  pointer_owner=GAME/PLUGIN
```

最关键的是：

```text
pointer_owner=GAME
```

是否出现在当前错误的武器/弹药对象上。

### 6.2 同一对象换内容

```text
HUD_GETTEXT_SELF_TRANSITION self=...
    old_source=Silenced P99
    new_source=MP7
    old_ptr=...
    new_ptr=...
```

若出现，它会直接证明 HUD 对象复用确实存在，并为“为什么早期常驻 LOC 指针有风险”提供实机证据。

### 6.3 技术身份延迟

```text
HUD_IDENTITY_DEFER_GETTEXT ...
reason=SOURCE_FIRST_HASH_DISAGREEMENT
 delivery=SUBMIT_EXACT_CONTEXT
 game_pointer=PRESERVED
```

这条日志说明：**不是中文没选到，而是中文被有意延迟到 SubmitText。**

### 6.4 SubmitText

动态数值：

```text
HUD_SUBMIT_TRACE ... kind=DYNAMIC_SCALAR
route=GAME_OWNED_BYPASS stable=SKIPPED
```

技术身份：

```text
HUD_SUBMIT_TRACE ... kind=TECHNICAL_IDENTITY
translated=1
source=Silenced P99
effective=消音P99
```

其中 `translated` 按 `wcscmp` 内容判断，不再按指针地址判断。

## 8. 实机结果决策树

### 结果 A：武器名和弹药都恢复

W1 路线成立。下一版可以：

- 保留两条窄生命周期规则；
- 把 LifecycleProbe 默认改为 0；
- 做长时间关卡回归后晋升 R10.4 后续稳定基线。

### 结果 B：武器名恢复，弹药仍不更新

说明“技术身份 label pointer 生命周期”已经命中，但弹药有独立数值路径。下一步：

- 查看是否有 `HUD_GETTEXT_TRACE kind=DYNAMIC_SCALAR`；
- 查看 `HUD_SUBMIT_TRACE ... DYNAMIC_SCALAR ... stable=SKIPPED`；
- 若都有，继续定位 UIWeaponPanel 数值缓存/绘制对象；
- 若都没有，证明弹药绕过当前 GetText/SubmitText，直接逆 UIWeaponPanel 数值链。

此时**不要扩大翻译 resolver**。

### 结果 C：弹药恢复，武器名仍乱

说明 scalar stable-pool 确有问题，但 weapon label 还有别的 object cache。重点看：

```text
HUD_GETTEXT_SELF_TRANSITION
HUD_GETTEXT_TRACE pointer_owner
HUD_IDENTITY_DEFER_GETTEXT
```

如果 P99 复现点没有触发 defer，使用日志中的实际 source/hash 进一步缩小条件，而不是全局回滚 Source First。

### 结果 D：任何已稳定中文回退英语

本候选直接判 FAIL，不晋升。优先从触发该英语的 W1 gate 找最小过宽条件；不得用“武器修好了”作为接受中文回归的理由。

从“版本差异 + R8 成功日志 + R10.4 当前日志”三者交叉看，最值得验证的不是再发明一套武器名称选择器，而是：
