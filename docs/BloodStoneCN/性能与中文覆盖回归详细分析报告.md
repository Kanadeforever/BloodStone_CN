# R10.4 W1.2a 英文回归与 W1.2b 回滚分析报告

> 日期：2026-08-16  
> 结论：W1.2/W1.2a 的性能优化改变了 R10.4/W1.1 的文本消费语义，已被实机否决；W1.2b 回滚全部语义性优化，只保留关闭高频诊断。

## 1. 实机现象

W1.1 已确认：中文字体恢复，枪械问题目前看来恢复。其主要未解决问题是中英混杂，另有进入关卡选择界面后 FPS 下降到 20+。

W1.2/W1.2a 为此加入 TextCoverage 热路径优化与混杂 guard。W1.2a 实机随后出现：

1. 关卡选择界面英文回归；
2. W1.1 仍正常的任务说明英文回归。

这两项属于不可接受的“已有中文回退”，因此 W1.2a 直接判定失败。

## 2. W1.1 -> W1.2a 运行时差异审计

真正会改变可见文本结果的变化只有三组。

### 2.1 Authoritative pointer fastpath

W1.2a 新增：只要 SubmitText 收到的 `wchar_t*` 地址恰好来自 loose LOC 容器，就直接调用原始 SubmitText，不再执行 `ResolveSubmittedText + TextCoverage`。

这一假设错误。R10.4/W1.1 的真实设计是：GetText 的 LOC 结果有时仍只是结构 carrier 或中间文本，后续 SubmitText TextCoverage 还会补齐任务字段、关卡/目标说明、动作 token、speaker/body 等。

因此“来自 LOC”不等价于“最终文本”，地址身份不能作为跳过 TextCoverage 的充分条件。关卡选择和任务说明的英文回归与此高度一致。

### 2.2 ThreadCoverageCache

W1.2a 还把 SubmitText coverage 结果按当前字符串做线程本地正/负缓存。即使算法理论上 deterministic，这仍改变了 W1.1 的执行时机与上下文消费顺序，尤其 precise/deferred mapping 是有时间窗口和线程上下文的。中文可靠优先阶段没有必要承担这一风险。

W1.2b 完整撤销。

### 2.3 Sparse mixed guard / pristine retry

W1.2a 为阻断 `... friendly 或 working ...`，在 resolver 结果和最终 effective 文本上增加“长英语只混入少量 CJK”拒绝。如果完整救援失败，会回到未经处理的原始英语。

这在策略上直接违反项目最高约束：不能用“纯英语”替换“虽然有污染但已有中文”的情况，更不能因此让 W1.1 已正常任务说明回退。

W1.2b 完整撤销。

## 3. 为什么 W1.2b 只关高频诊断

W1.1 日志显示 `LifecycleProbe=1` 时，动态弹药每几十毫秒产生 `HUD_GETTEXT_TRACE / HUD_GETTEXT_SELF_TRANSITION / HUD_SUBMIT_TRACE`，每条都经过日志锁、UTF-8 格式化和 `WriteFile`。关卡选择界面又是高频 UI 提交场景，因此先做“只关诊断、不改文本语义”的 A/B 才是正确实验。

W1.2b 默认：

```ini
LogMisses=0
LogActionTokens=0
LifecycleProbe=0
```

而决定文本结果的 `external_loc.cpp / submit_text_bridge.cpp / text_coverage_resolver.cpp` 直接恢复 W1.1。

## 4. 中英混杂下一步

中英混杂仍是 P0，但不能再用全局结果过滤器。下一步应从 W1.2b/W1.1 的原链上定位混杂究竟来自：

- recent precise mapping；
- global deferred mapping；
- TextCoverage 某个具体 mode；
- 已经污染的 LOC/BLI 关系。

只在明确来源处阻断错误的一次局部替换，同时允许后续完整中文 resolver 继续运行。必要时增加**仅在检测到稀疏混杂时触发、总量有上限**的来源日志，不再开启逐帧 HUD 全量探针。

## 5. W1.2b 验收顺序

1. 关卡选择中文恢复；
2. 任务说明中文恢复；
3. 枪械/弹药仍正常；
4. 字体无口口口；
5. 关卡选择 FPS 与无 BSCN 对照；
6. 收集仍存在的中英混杂样本，进入下一轮窄修。
