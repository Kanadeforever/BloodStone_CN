# 2. 项目目标、工程边界与不可变原则

## 2.1 总目标

在不直接修改 `Bond.exe` 的前提下，为 PC 版 **007 Blood Stone (2010)** 提供完整简体中文运行环境，包括：

- 中文字形；
- 中文排版；
- LOC 文本覆盖；
- 动态任务/教程/动作提示；
- 剧情字幕；
- 普通 NPC 场景对白字幕；
- 与独立手柄图标插件并存；
- D3D9 Reset / 分辨率切换 / 长时间运行的稳定性；
- 尽量兼容未来 Windows 与 DXVK 等环境。

## 2.2 翻译正文与程序逻辑的边界

当前工程已经形成非常明确的原则：

### LOC 是最终译文真源

现有 **86 个 `.loc`** 是完整初翻测试内容的权威源。

程序技术层的职责是：

- 正确加载；
- 正确关联；
- 正确选择上下文；
- 正确进入最终 UI；
- 保持游戏原始生命周期；
- 正确显示。

技术层**不应该通过 C++ 硬编码正文来补翻译**。

### BLI3 不是最终译文库

`loc_context.bli` / BSCNLI3 的职责是：

- 原英语 source；
- key/hash；
- 上下文；
- defer 信息；
- 历史 replacement 指纹；
- 歧义消解辅助。

已知统计：

```text
records             = 7665
hashes              = 7655
ambiguous_hashes    = 10
historical deferred = 221
```

R7 之后正确原则是：

```text
当前 LOC 决定最终中文
BLI3 只帮助证明“是哪一条”
无法证明时 NO_GUESS
禁止 FIRST_BLI_CANDIDATE
```

## 2.3 “已有中文不能回英语”是最高回归门槛

这一原则在 W1.2a 事故后被再次强化：

> 不能为了让一种混杂文本“看起来干净”，把已经存在部分中文的结果直接退回整句英语；更不能让 W1.1 已正常的关卡选择、任务说明回到英语。

因此：

- 武器修好了但任务回英语：FAIL；
- FPS 恢复但中文覆盖下降：FAIL；
- Mixed Guard 让污染文本退英语：FAIL；
- 缓存使已有 TextCoverage 不再运行：FAIL。

# 3. 游戏与资源系统基础事实

## 3.1 可执行文件与渲染

早期逆向已确认：

- `Bond.exe`：32 位 PE；
- `.text` 中存在由 `rld.dll` 运行时处理/解密的部分；
- 渲染 API：Direct3D 9；
- 字体是游戏自定义资源系统；
- PAK 为 Bizarre Creations 的 2KAP 体系；
- 研究中确认过 XOR + zlib 等打包特征。

当前所有 ASI 必须按 **Win32/x86** 设计，不得误编译 x64。

## 3.2 早期原生字体资源

`root.pak` 中确认存在：

```text
ui_font_ba.bpr   ≈688 KB    1024×512    DXT1   BA / Latin
ui_font_ba.dat   ≈17 KB

ui_font_ea.bpr   ≈1376 KB   1024×1024   DXT1   EA / 含日文
ui_font_ea.dat   ≈38 KB
```

早期结论：PC 版正常路径只实际使用 BA 字体，EA 字体虽存在于资源内，但并没有像预想那样直接成为 PC 日文字形解决方案。

这解释了为什么“直接让游戏读 EA 日文字库”长期没有形成可用汉化路线。

## 3.3 BPR 的关键格式事实

BPR 标识为 `2RZB`，其中 DXT1 块不是标准字节序。

BPR 原始块：

```text
[LUT0][LUT1][LUT2][c0_lo][c0_hi][c1_lo][c1_hi][LUT3]
```

标准 DXT1：

```text
[c0_lo][c0_hi][c1_lo][c1_hi][LUT0][LUT1][LUT2][LUT3]
```

该重排已经被历史工具验证，可把 BPR 正确解码成标准纹理数据。

## 3.4 DAT 与 BuildGlyph

DAT 与 BPR 分离，历史分析确认 glyph entry 大约为 **28 字节**。

运行时曾捕获到：

```text
BuildGlyph 条目约 304 个
每条约 108 bytes
整体分配约 62 KB
```

早期研究一度把“304 slot”视为 CJK 扩容的核心瓶颈，但后续 BFA + NativeGlyph 架构已经绕过了“必须扩原始 304 槽才能做中文”的限制。

因此：

> **304 slot 是重要历史逆向证据，但不是当前主线的核心阻塞项。**

# 4. 早期 D3D9 字体研究：哪些仍有价值，哪些已被新架构取代

## 4.1 早期已经成功验证的 Atlas 替换证据

早期 `A → ア` 实验是第一个“游戏里真实显示出预期非拉丁字形”的关键里程碑。

当时确认文本渲染大致为：

```text
SetTexture(stage=0, font texture)
→ SetFVF(0x104 = XYZRHW | TEX1)
→ DrawPrimitive(TriangleList)
```

字体顶点约 24 bytes：

```cpp
struct FontVertex {
    float x, y, z, rhw;
    float u, v;
};
```

早期 hook 链：

```text
Bond.exe IAT Direct3DCreate9
    ↓
IDirect3D9::CreateDevice   vt[16]
    ↓
IDirect3DDevice9
    ├─ CreateTexture       vt[23]
    ├─ CreateVertexBuffer  vt[26]
    ├─ SetTexture          vt[65]
    ├─ DrawPrimitive       vt[81]
    ├─ DrawIndexedPrimitive vt[82]
    ├─ DrawPrimitiveUP     vt[83]
    └─ SetFVF              vt[89]
```

## 4.2 早期失败路线

以下已经验证不能作为现行主线：

### 直接 PAK 字体注入

替换 BPR/DAT 并不能自动让 PC 原生字体管理器正确使用完整 EA/CJK 结构。

### 直接修改 BuildGlyph 缓冲

HeapAlloc 追到 304 条记录后修改内存，画面没有随之改变，说明 Font Manager 后续还会转换/缓存内部结构。

### 误判 1024×512 纹理

早期曾把 UI 图集和字体 runtime atlas 混淆。

### CPU 读取 D3DPOOL_DEFAULT 动态 VB

字体确实走 DrawPrimitive，但 CPU 侧并不能按普通系统内存方式直接读取 D3DPOOL_DEFAULT 动态 VB。

## 4.3 现行意义

这些研究最终留下两类仍然重要的成果：

1. D3D9 hook / vtable / Reset 生命周期经验；
2. 证明“外挂可以接管字形资源而不修改 Bond.exe”的可行性。

真正生产架构后来已经升级为：

```text
BFA 2048×2048 字库
+ NativeGlyph 运行时注入
+ D3D9 纹理生命周期管理
```

而不是继续使用最初的“SetTexture 粗替换”方案。

# 5. OLTX `.loc` 格式

## 5.1 基本结构

OLTX 是 Bizarre Creations 使用的多语言本地化容器。

确认过的样本包含 8 个语言块：

```text
en fr de it ja pl ru es
```

典型结构：

```text
Header
Language Directory (8 × 24 bytes)
Key Table
EN Block
FR Block
DE Block
IT Block
JA Block
PL Block
RU Block
ES Block
```

Header 已确认的主要字段：

| 偏移 | 大小 | 含义 |
|---|---:|---|
| `0x00` | 4 | `OLTX` |
| `0x04` | 4 | version = 1 |
| `0x08` | 4 | 常见 `0x10` |
| `0x0C` | 4 | 文件大小相关字段 |
| `0x10` | 4 | entry count 相关 |
| `0x14` | 4 | stride，样本为 8 |
| `0x18` | 4 | key table offset |

字符串内容是 UTF-16LE。

## 5.2 当前汉化如何使用 LOC

测试阶段把中文放在 PC 版实际读取的 `en` 槽中。

生产目录在 R7.1 之后统一为：

```text
scripts\
├─ BloodstoneCN.asi
├─ BloodstoneCN.ini
└─ BSCNContents\
   ├─ fonts.bfa
   ├─ loc_context.bli
   └─ loc\
      └─ ... 86 个 .loc
```

R9 典型配置：

```ini
AtlasFile=BSCNContents\fonts.bfa
Root=BSCNContents\loc
Index=BSCNContents\loc_context.bli
```

# 6. 中文字库、BFA 与 M2F1 排版基线

## 6.1 BFA

已批准的 BFA 基础特征：

```text
magic      = BSCNATL1
atlas      = 2048 × 2048
glyphs     = 2512
```

历史稳定 BFA SHA-256：

```text
bfe43d2aafed75741ca275d1d7eadf0ee3297b4165e968eee8cb13f0340c7f85
```

这是一条重要的资源基准值；后续若重建字库，应明确说明是否仍然是同一字形集合/网格策略，而不能把新生成文件静默当成旧基线。

## 6.2 M2F1 是已实机确认的字距基线

用户曾明确确认：

> “OK，现在没问题了，字距基本都是正确的”

M2F1 冻结公式：

```cpp
glyph.field08 = source->bearing_x;
glyph.field0c = source->width;
glyph.field10 = source->advance_x - source->bearing_x - source->width;
```

渲染器有效前进量：

```text
field08 + field0C + field10 = advance_x
```

在标准网格常见 CJK 记录上，日志出现过：

```text
field08 = 0
field0C = 36
field10 = -4
sum     = 32
size    = 36×44
```

## 6.3 禁止重新引入的全局 spacing Hook

已明确禁止把下列地址重新作为全局字距修补主线：

```text
0x00E85392
0x00E85469
0x00E85484
0x00E8536C
```

原因是历史 R5M 系列已经证明：

- 直接改最终位移容易影响中英文边界；
- kerning、tracking、advance 不应混成一个总偏移；
- 负固定字距可能让居中字幕、右对齐、换行整体漂移；
- 某些 Hook 观察到的是样式 tracking，而不是最终 cursor advance。

## 6.4 NativeGlyph 关键地址

现行字体桥长期使用的关键点：

```text
NativeGlyph lookup slot       0x011A02D8
texture resource resolve CALL 0x00E42C21
custom resource handle        0xBFFF
font owner resource handle    +0x12C
texture resource pointer      +0x08
```

游戏原生已有 Unicode glyph 时应优先保留 native glyph；缺少的字符再由 BFA 提供。

```text
zzz_BloodstoneCN_TextCoverage_T3.asi ≈27 KB
```

两者同时运行曾被用户确认非常正常。

T3 能处理的典型内容包括：

- 城市名；
- `%d / %d Intelligence`；
- 教程模板；
- speaker/body；
- 动作提示等。

但 T3 的 `FIRST_BLI_CANDIDATE` 等策略后来被证明存在歧义风险，不能原样作为最终算法。

## 8.2 T4 PE 二进制拼接：永久失败路线

曾尝试把两个 ASI 用 PE section/binary merge 方式硬拼成一个文件，出现 `0xc000007b` 等问题。

结论：

> **永久禁止二进制拼接、section injection、自制 PE merge 来“合并两个插件”。**

正确合并方式必须是**源码层合并后重新正常链接成一个 PE32 DLL**。

## 8.3 T5 大类重构：失败

T5 曾出现：

- 编译产物约 280 KB，明显异常膨胀；
- 游戏只加载约 30～36 KB 后崩溃/无法正常工作；
- 重组方向偏离原稳定结构。

用户明确同意废除 T5。

## 8.4 R3：恢复真正的 loose LOC Loader

R2 的重大问题是只恢复了 BSCNLI3，而没有恢复原 M2F1 的 loose LOC Loader。

R3 恢复：

```text

+ LoadLocFile
```

正常日志目标：


R3 正确区分：


## 8.5 R4：规范化、组合段、printf 与跨线程 deferred

R4 的主要改进：

### 规范化索引从全部权威记录建立

只有当 normalized source 始终对应唯一 replacement 时才允许使用；一旦出现不同 replacement，整个 normalized key 排除。

### 组合正文

只支持已经观察过的可见分隔符：

```text
" / "
" - "
```

每一段都必须独立安全命中，否则整串保持原样。

### `recent_precise_printf`

针对：

```text
GetText:   模板含 %s
游戏格式化后
SubmitText: 已经看不到字面 %s
```

R4 用最近一次**原始 key/hash 精确上下文**重建最终 formatted replacement，而不是把该模板提升为全局 source fallback。

### 过场字幕跨线程 deferred

研究阶段为了找电影字幕调用链，曾增加跨线程小环缓存。

## 8.6 R5：第一次明确“resolver hit 不等于画面成功”

R5 建立了非常重要的五层成功判据：

```text
Level 1  resolver hit
Level 2  stable SubmitText
Level 3  UIDialogue final buffer
Level 4  Renderer association
Level 5  用户实机可见中文
```

最终只有 Level 5 才能称“问题解决”。

R5 还发现：如果游戏在 `SubmitText` 返回后继续保存传入 `wchar_t*`，局部 `std::wstring` 会变成悬空指针。因此加入进程期稳定字符串池。

## 8.7 R6：修掉“假 translated”与半翻译

R6 修正几个关键问题：

1. `translated=1` 必须以 UTF-16 **内容变化**判断，不能仅凭指针变化；
2. deterministic whole-source TextCoverage 应在某些 precise/deferred fallback 前运行；
3. `Speaker: body` 必须整条安全成功或整条保持原样，不能只翻 speaker；
4. UIDialogue 最终对象不允许 broad partial mapping；
5. printf 模板只有同一 source 的全部 replacement template 完全一致时才作为全局安全模板。

### R7：LOC authoritative

### R7.2：P99/MP7 与过场回归安全版

- 某实时过场出现镜头流程异常。


## 8.10 R9：HookConsolidation + Coverage


# 9. R10 / R10.4：从“短型号黑名单”升级到通用 source identity

R10 正式把 R7.2 的短型号守恒升级成通用身份模型。

正确方向：

```text
native original source
    ↓
exact BLI source family
    ↓
primary/secondary hash 只在该 source family 内消歧
    ↓
若 hash 不能证明，则只在同 family 的 current LOC + flags 可安全唯一时选
    ↓
否则 NO_GUESS
```

这意味着：

- 不应该靠 P99、MP7、M16 等武器名单维护正确性；
- “原始 source 是谁”比缓存 hash 更接近真实对象身份；
- hash 只能作为 source family 内的辅助信息。

R10.4 在此基础上继续扩大已有中文覆盖，成为后续 W1 修复必须保留的能力基线。

### 不能简单回滚 R9/R8

R9 并不是经过当前所有武器/弹药/任务/教程矩阵验证的“黄金版”。

因此后续原则是：

> **只从旧版考古“哪个生命周期保护曾经正确”，不能整体把 R10.4 文本能力倒退回旧版本。**

# 11. 预渲染 CG 字幕时长问题

用户长期观察：

```text
即时演算字幕：基本正常
预渲染 CG：中文字幕比语音消失得早
```

一个高度合理并被架构使用的解释是：

- 游戏在较早阶段按原字符串长度估算字幕持续时间；
- 如果 GetText 很早就返回更短中文，时长会随之缩短；
- 因此应尽量让原英语继续经过计时/格式化逻辑，最终显示阶段再中文化。

R9 的 auto-defer 正是这个方向。

这条经验仍应保留：

> **字幕文字替换的“正确时间点”与“正确内容”同样重要。**

不要轻易恢复旧 timing loop 粗暴 Hook，除非先证明 auto-defer 无法覆盖具体 CG 路径。

# 12. FontOnly loose gamedata 实验：为什么值得做、为什么最终失败

2026-08-14 曾进行一次架构重写验证：

```text
完整 loose gamedata
+ 中文 LOC 覆盖原路径
→ 让 Bond.exe 自己处理所有 GetText/token/任务/HUD/SubmitText

BloodstoneCN.asi
→ 只负责 fonts.bfa + NativeGlyph
```

它的理论优点非常明显：

- 武器身份由游戏真实 key 决定；
- 弹药数字永远不被 ASI 稳定化；
- 任务模板由原生系统处理；
- 动态 token 由游戏自己格式化；
- BSCN 不再需要 source/hash 猜测；
- TextCoverage 性能成本从结构上消失。

FontOnly 明确删除：

```text
GetText 0x00E87740 hook
SubmitText 0x00E85900 hook
ExternalLoc
BLI3
TextCoverage
recent/deferred context
stable replacement buffer
source identity resolver
EndScene interop host
```

只保留：

```text
BFA
Direct3DCreate9
CreateDevice
Reset
NativeGlyph 0x011A02D8
resource resolve 0x00E42C21
```

但是后续实机已经判明：

> **当前 loose gamedata / native LOC 路线没有按设想成为完整可用替代方案。**

因此 FontOnly 不是现行架构，只能保留为失败实验和未来如果重新确认资源优先级时的参考。

# 13. R11 / R11.1 / R11.2 / R11.3：为什么必须归档为失败实验

这是本次汇总最容易被误读的一段，因为 R11 编号更大、文档更多，但**最终结论明确是失败并停止**。

## 13.1 R11 的目标

R11 试图把 R10.x 多层 resolver 重构成更“干净”的：

```text
Source Identity
+ Final Text Resolver
+ 独立 D3D 生命周期
```

并解决 BSCN/NPC 的 D3D hook 互操作。

## 13.2 R11.1 的严重回归

源码审计确认，R11.0/11.1 又犯了历史上已经出现过的错误：

> **把 source→replacement 关系压平，丢失 BLI3 语境与当前 LOC 的正确一一关系。**

后果包括已解决过的：

- Switch / Vault 等动作提示；
- Focus Aim；
- speaker/body；
- 任务文本；
- 其他 TextCoverage 路径

重新回归。

## 13.3 R11.2 仍缺最终 UI 对象层

进一步审计发现 R11.2 的核心问题不是“再少几个规则”，而是重构时删掉了实际需要的最终 UI 对象/最终消费补链。

## 13.4 R11.3 与 NPC 互操作仍暴露架构级问题

R11.3 尝试恢复最终显示并修 NPC interop，但实机/源码继续暴露：

- final-object 虽进入但结果仍不完整；
- NPC standalone fallback 的 D3D hook 安装存在非原子链问题；
- NPC 看到 BSCN 文件后等待 host，但 R11.1/11.2 又移除了 host export；
- 可能导致真实 D3D Device 已创建后 NPC 才尝试 bootstrap，最终 Dialogue 能抓到但没有 EndScene 可画。

## 13.5 最终裁决

会话中已经写出明确结论：

> **R11 生产重构失败，正式停止。回 R8/R10.4 体系继续修。**

因此后续：

- 不得因为 R11 “代码更干净”而恢复；
- R11 的 CAS 链式 hook、独立 D3D 等局部技术可以抽取；
- 但不能带回它的 CleanResolver 文本语义。

# 14. 武器 HUD / 弹药生命周期：W1 的真正价值

R10.4 后期最棘手的回归之一：

- `Silenced P99`、MP7、MP5 等在同一 HUD 对象上复用；
- runtime hash 可能 stale；
- 弹药数字是高频动态 scalar；
- 如果把所有替换结果塞进长期 stable pool，可能冻结动态数值或污染对象身份。

## 14.1 历史 R8 已给出的关键实机证据

日志曾出现同一 hash pair：

```text
primary=0x033DAF32 secondary=0x24DE92C2 source=MP7
primary=0x033DAF32 secondary=0x24DE92C2 source=Silenced P99
```

这证明 hash pair 不能独立代表当前 HUD 文本身份。

R7.2 当时通过 short-code guard 让游戏自己的 `Silenced P99` 继续向后走，最终 TextCoverage 仍能得到：

```text
消音P99
```

因此最重要的历史经验是：

> **保留 game-owned source / pointer 生命周期，再晚一点中文化，是已经有实机成功先例的策略。**

## 14.2 W1 的基本策略

对疑似动态 HUD 身份文本：

```text
GetText 阶段
如果 source 与 hash 状态不可信
→ 保留游戏原 pointer
→ 不在这里把对象身份硬替换成中文 stable pointer

SubmitText 阶段
→ 使用更完整的实时上下文中文化最终可见文本
```

对动态 scalar（如弹药数字）：

```text
GAME_OWNED_BYPASS
stable = SKIPPED
```

即：

> **数值继续由游戏自己持有，绝不能塞入永久字符串池。**

## 14.3 W1 实机方向基本正确

W1.1 日志曾显示：

```text
SOURCE_FIRST_HASH_DISAGREEMENT ... original=Silenced P99
HUD_IDENTITY_DEFER_GETTEXT ... replacement=消音P99 ... game_pointer=PRESERVED
HUD_GETTEXT_TRACE ... source=Silenced P99 pointer_owner=GAME
HUD_SUBMIT_TRACE ... source=Silenced P99 effective=消音P99
```

同一 `self` 还会在不同枪械之间反复变化。

这恰恰证明：

- UI 对象本身会复用；
- 当前 source 才是实时语义；
- 生命周期保护不能以“这个 self 上次是什么”永久锁定。

# 17. W1.2 / W1.2a：为什么静态全 PASS 仍然必须判失败

W1.2 为了性能和 mixed text 做了三类变化：

## 17.1 Authoritative pointer fastpath

思路：

> SubmitText 如果收到的指针地址来自 loose LOC 容器，就认为已经是最终中文，直接跳过后续 TextCoverage。

问题：

> **“来自 LOC”不等于“已经是最终显示文本”。**

很多 LOC 结果仍然只是：

- carrier；
- 中间模板；
- 任务结构；
- speaker/body 组件；
- 后续需要 TextCoverage 补齐的阶段文本。

这正是关卡选择、任务说明英文回归的最合理根因之一。

## 17.2 ThreadCoverageCache

按当前字符串做线程本地正/负缓存，看似算法 deterministic，但仍然改变了：

- precise/deferred mapping 的消费时机；
- 短时间窗口；
- 线程上下文；
- 后续模式是否还有机会运行。

在“中文可靠优先”阶段，这种语义级缓存风险过高。

## 17.3 Sparse mixed guard / pristine retry

W1.2 尝试把：

```text
长纯英语
→ 只混入 1～4 个 CJK
```

判为 sparse partial 并拒绝。

问题是：如果完整救援失败，它可能回到纯英语。

这直接违反：

> “不能为了清理混杂，把已有中文整体退回英语。”

## 17.4 W1.2 编译错误与 W1.2a

W1.2 初始源码 `submit_text_bridge.cpp` 的 `Forward()` 内漏了一枚闭合 `}`，导致 MSVC C2601/C1075。

W1.2a 只补该花括号，并新增逐 `.cpp` 花括号结构验证。

静态结果：

```text
源码/合同/结构验证 58/58 PASS
R10.4 文本模型 31/31 PASS
Clang -fsyntax-only PASS
```

但实机马上出现：

```text
关卡选择界面英文回归
```

# 20. 性能审计：哪些优化是安全的，哪些不安全

## 20.1 BSCN test1g 遗留的纯冗余 NPC 去重热路径

NPC P1 已不再依赖 BSCN SubmitText 判断“是否显示”，但 test1g 的 BSCN 还在每次 GetText/SubmitText：

```text
GetText
→ mutex
→ 复制 key/source/replacement 到 128 项 ring

SubmitText
→ 构造 std::wstring
→ 最多扫描 128 项 recent mapping
→ 字符串比较 / hash
→ 再写 recent ring
```

P1 已完全不消费这些数据。

`test1h` 删除了这整套正常热路径，只保留 BSCN/NPC 的真正 D3D9 生命周期互操作：

```text
DeviceCreated
BeforeReset
AfterReset
EndScene
```

这类优化属于：

> **删除已经没有消费者的纯冗余工作，不改变文本语义。**

因此风险明显低于 W1.2 的 TextCoverage fastpath/cache。

## 20.2 通用对象身份保护去堆分配

test1g 某些 GetText 命中会做：

```text
wstring / vector / substr
```

`test1h` 改成 span 扫描，目标是**保持完全相同的判定规则但不做堆分配**。

这类“实现等价、减少分配”的优化属于更安全方向。

## 20.3 NPC P1 renderer 的双 StateBlock

P1 活动字幕时每帧曾做：

```text
shadow:
CreateStateBlock(D3DSBT_ALL)
Capture
Draw
Apply
Release

main:
再做一整套
```

即一条字幕期间，每帧创建两套完整 D3D9 StateBlock。

同时每帧还会：

```text
mutex
vector<Slot>
复制 std::wstring
sort
```

P1a 改为：

```text
每个 Device 只创建一个 StateBlock
活动帧：Capture 1 次
→ 画所有 shadow + main
→ Apply 1 次
```

并新增：

```text
active_until
```

无字幕时 EndScene：

```text
一个原子时间判断
→ 直接返回
```

不再碰 slot mutex。

字幕正文也在 Enqueue 时建立 immutable storage，不再每帧复制。

## 20.4 Semantic Probe 隐藏成本

P1 默认：

```ini
LogEveryEvent=0
```

原实现虽然只写一次日志，但每次 Dialogue 仍然执行完整 `ReadProcessMemory` 深探针。

P1a 改为：

```text
同 dialogue hash 第一次
→ SemanticSnapshot + route owner
→ 缓存

后续同 hash
→ 直接复用
```

需要专项研究“同 hash 是否不同上下文”时，再把：

```ini
LogEveryEvent=1
```

打开。

## 20.5 安全性能优化边界

### 可以优先做

- 关闭发行默认高频日志；
- 删除已经没有消费者的 ring/cache；
- 无字幕时原子 early-out；
- StateBlock 复用；
- immutable storage；
- 等价 span 扫描替代临时 string/vector；
- 深探针按稳定 key 缓存。

### 暂时不要做

- 用指针来源推断“已经是最终文本”；
- TextCoverage 正/负缓存改变 resolver 时序；
- 为了 FPS 跳过某些 coverage mode；
- Mixed Guard 最终出口退英语；
- 以“已经翻过一次”为理由永远阻止后续完整 resolver。

# 21. NPC 场景字幕：已经确认的底层事实

## 21.1 普通 NPC / 场景对白 key 已打通

Probe2 / Probe3 已确认：

> **普通 NPC、路人和场景对白触发参数中的 `DIALOGUE.arg0`，就是对应 `*_script_dialogue.loc` 的 `key_hash`。**

这一结论让 NPC 字幕不再需要“扫描屏幕上出现的字符串”来猜文本，而可以：

```text
Dialogue event
→ arg0 key_hash
→ 读取对应 script_dialogue.loc
→ 找中文
→ 决定是否需要自绘字幕
```

历史研究地址包括：

```text
Dialogue lookup / event path 0x00F12820
已观察 callsite          0x0093A2A1
```

这些地址属于静态逆向证据；后续若换 exe，仍应做签名/版本验证，不能把绝对地址当跨版本 ABI。

## 21.2 为什么 NPC 字幕不能简单“全都画”

默认必须排除更可能已有原生字幕/通信 UI 的内容：

- BOND；

- 主线无线电；
- 教程；
- 任务提示；
- 已由游戏原生字幕系统显示的剧情通信。

否则会出现：

```text
原生字幕 + NPC overlay 双重显示
```

因此后来发展出**语义分流**，而不是继续维护粗暴名字黑名单。

# 25. BondGamepadIcons：独立支线完整结论

GamepadIcons 不属于主汉化文本 resolver，后续 BSCN 修复原则上**不应修改其功能**。

## 25.1 三家族抽象

已经形成：

```text
Auto
Xbox
PlayStation
Nintendo
```

自动 family 的目标映射：

```text
PlayStation → PS5 图集
Nintendo    → Switch 图集
Xbox/未知/无 SDL → Xbox 图集
```

## 25.2 命令行覆盖

```text
Bond.exe -ps
Bond.exe -ns
Bond.exe -xb
Bond.exe -auto
```

规则：

- 独立完整参数匹配；
- 不区分大小写；
- 多个有效参数同时出现时**最后一个有效参数生效**；
- 命令行 > INI > Auto > Xbox fallback。

## 25.3 无 INI 默认

最终方向：

```text
Enable=1
EnableLog=0
IconStyle=Auto
```

无 SDL/无法识别时回 Xbox。

## 25.4 自动 family 的分层判断思想

设计上不只依赖一个 SDL enum，而按：

```text
已知有效 SDL mapped type
→ SDL type string（兼容未来类型）
→ PlayStation 特征按钮标签
→ SDL real type
→ 名称/VID 等低优先级回退
→ Xbox 默认
```

重要原则：

> 如果 SDL 的**有效映射类型**明确把某个物理设备按 Xbox 处理，则图标也应按 Xbox；真实厂商 VID 不应反过来覆盖 mapped type。

这让未来 PS6、Switch2 等只要 SDL type string 仍有家族特征，就有机会无需重新编译插件而归类到现有三大家族。

## 25.5 保留的映射不变量

已长期作为回归项：

```text
Tips LT / RT
过场 Y / START
掩体教程 action 38/39 → LS_LEFT / LS_RIGHT
黑客 QTE action 38/39 → A / X
初始瞄准 → LT + RS_ALL
无限弹药 (3,7) 保持原图
UseJoypad=0 → 游戏原生键鼠图标
```

## 25.6 UPX 专项

v1.4.17 未压缩版可运行，但 UPX 压缩后曾出现：

```text
内存约 40 MB
→ 降至约 9 MB
→ 崩溃
```

v1.4.18 针对：

- C++ `thread_local` 静态 TLS；
- DLL thread notifications；
- 额外 SDL observer thread；

进行修复：

- 动态 TLS (`TlsAlloc/TlsGetValue/TlsSetValue`)；
- `/Zc:threadSafeInit-`；
- PE TLS Directory 必须为 0；
- `DisableThreadLibraryCalls`；
- SDL family 观察合并进唯一 worker thread；
- packed/unpacked 都做 PE 检查。

## 25.7 v1.4.19 → v1.4.20 Reset 恶性 BUG

用户发现：

> 游戏中切换分辨率后，手柄图标消失。

v1.4.19 的 `HookDeviceReset()` 在真正 Reset 前：

```cpp
ReleaseDeviceTextureCandidatesLocked();
```

会把：

- 已确认 atlas；
- sourcePixels；
- Xbox/PS/Switch 三套替换纹理；

全部忘掉。

但实机目标 atlas 是：

```text
512×512
DXT5
D3DPOOL_MANAGED
CRC32=0x29F36B36
```

`D3DPOOL_MANAGED` 本来就会跨普通 Reset 保留，于是：

```text
ASI 忘掉图集
游戏 managed texture 仍活着
游戏不会重新 CreateTexture
ASI 再也发现不了它
→ 图标永久丢失
```

### v1.4.20 修复

Reset 改成事务式：

```text
Reset 前：不释放 managed atlas
调用原 Reset
├─ 失败 → 状态原样保留
└─ 成功
   ├─ 保留 managed 原图集
   ├─ 保留 atlasConfirmed
   ├─ 保留 sourcePixels
   ├─ 保留最后 stage
   ├─ 保留 Xbox/PS/NS 缓存
   ├─ 未确认 managed candidate 重开扫描窗口
   └─ 仅清理不能跨 Reset 的非-managed candidate
```

v1.4.20 静态验证和现有 harness 已通过；资料中的最后动作是要求用户实机：

```text
正常显示
→ 切一次分辨率
→ 看 Tips/教程
→ 再切一次分辨率
```

因此应写成：

> **v1.4.20 是 Reset 修复候选，不要把“静态 PASS”写成“用户已完成实机封版”。**

# 36. 最终工程原则

这个项目已经多次证明：

> **最危险的不是“少翻一条”，而是为了补一类文本，改变了游戏原有对象身份、字符串生命周期、计时或渲染时序，从而让另一类已正常内容回归。**

因此未来所有版本都应遵循：

1. **实机已通过的东西默认冻结；**
2. **任何新优化必须能说明自己是否改变文本消费语义；**
3. **身份问题优先保留游戏原对象，不猜；**
4. **动态数值不稳定化；**
5. **中文尽可能在最晚但仍可控的阶段交付；**
6. **性能优先删纯冗余，而不是删覆盖能力；**
7. **日志是临时研究工具，不是发行默认热路径；**
8. **每个包都必须独立接档，不能要求下一位开发者去翻几十个旧聊天才能知道哪些方案已经失败。**
