# NPC 环境对白多消息三行调度设计与验证

## 解决的问题

原本 `native_standalone.cpp` 只有 `g_text`、`g_last_hash`、`g_start`、`g_end` 一份正在显示的字幕缓存。每次 `AfterDialogue` 命中都会重写这些数据；旧的“最多三行”只是同一段文本换行。因此，多个人同时讲话时，新事件会在显示期限尚未结束时顶掉前一个人的字幕。

## 最终设计

`source/NPCSubtitles/src/subtitle_queue.h` 中的队列结构独立于 Windows、游戏数据和 D3D9。三个活动项各有哈希、文本、开始时间、持续时间。`Push` 在入队前清理过期项，并检查最近 800 毫秒内的相同哈希。屏幕尚未满三个活动项时立即展示，否则将完整正文按先进先出顺序写入最多 16 项的环形等待队列。

每次 D3D9 EndScene 开始绘制时，先短暂获取队列锁，删除过期项，将排队消息依次补齐，并复制当前三个活动项的快照；**所有字形查询、纹理引用、顶点绘制都在锁外完成**。等待消息只有真正升为活动消息时才重新设置开始时刻，从而不会因为已经在队列里等了一段时间而不显示。每条活动消息独立计时，较晚消息不改变较早消息的剩余时间。

## 三行排版

界面行数是一个整体预算，绝不超过 3。对于 N 个活动项，先给每个活动项一行，再把 `3-N` 个空闲行优先分给需要换行的较早消息。三条同时说话必定一人一行；两条时如果需要可以将较早长句换为两行；只存在一条时继续支持最多三行。若某个活动项在分配行数内无法按原字号显示全部字形，最后一行以水平方向自适应缩放，避免把其他对白顶出画面。

仍只使用游戏原有 EUR 字形和 D3D9 的一组顶点提交，保持白色笔画遮罩、阴影、共同基线以及 480p 参考字号、分辨率自动缩放逻辑。虽然最多三条消息，每帧也只有一次 StateBlock 保存／恢复和两次 DrawPrimitiveUP（阴影、正文）。

## 已完成的离线测试

`source/NPCSubtitles/tests/queue_native_test.cpp` 是直接调用实际队列头文件的原生 C++ 测试程序。通过 Python 驱动执行，已验证：三条同时入屏、第四条排队、800ms 哈希防重复、独立到期时间、FIFO 提升顺序、等待队列满载而不覆盖已有字幕、32 位时钟回绕、安全文本截断和 1/2/3 条对白的行预算规则。

v0.1e-log5 由 Clang/LLD 编译，三行调度当时未引入新游戏 Hook；v0.1e-log6 增加了过场事件监听，仍保留 `+0x1C` 原生剧情字幕分流、D3D9 状态恢复和 `--log` 日志门控。用户已实机验收三行消息不互相覆盖；v0.1e-log6 的新增过场清空已于 2026-10-11 实机通过并正式封版。

## 已知约束

等待队列容量为十六条，以免遭遇异常高频事件时无限分配内存；满载时新增对白被拒绝并在 `--log` 中报告。排队的对白可能在相应语音播放结束之后才显示；三条超长对白同时出现时字形可能因为压缩而偏小。不把这些情况伪称为全部解决。

## 过场时队列的生命周期

收到 `CutSceneStart` 后，对整个三行活动槽位与十六项 FIFO 等待队列执行 `subtitle_queue::Clear`，同时清除最近哈希去重状态。渲染线程在过场活动期间快速返回，事件线程也不再插入字幕。收到 `CutSceneEnd` 后恢复普通队列规则，旧字幕不会从等待队列再次弹出。

新增原生 C++ 测试实际验证三条可见字幕、一条等待字幕被一起清掉、Advance 不会复活旧字幕、结束后同一哈希可重新进入队列。队列本身不依赖游戏 API。游戏是否在全部过场类型发送对应事件尚待实机确认。
