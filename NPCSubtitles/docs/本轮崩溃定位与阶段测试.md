# NPCSubtitles v0.1c：Win32 x86 栈帧 ABI 修复与阶段 A 验证

## 一、用户实机日志与事实

用户已确认：

- `v0.1a` 的无 Hook 启动诊断插件能正常进入游戏，日志为 `BOOT_ATTACH_OK`、`NO_HOOKS_INSTALLED`。
- `v0.1a` 的功能版启动即崩溃。
- `v0.1b` 的阶段 A（没有安装任何 Hook）仍然崩溃；两个日志最后分别为：

```text
NPCSubtitles v0.1b stage=1 checkpoint=WORKER_THREAD_CREATED tick_ms=804464343
NPCSubtitles v0.1b stage=1 checkpoint=MODULE_PATH_OK tick_ms=804464343
```

`MODULE_PATH_OK` 后的旧代码是创建 `NPCSubtitles.log`，随后才会执行游戏 PE 验证、动态申请 NPC 索引、读取 LOC 和当时的 TSV；**当前版本不再读取 TSV**。**日志只能确定最后一个成功检查点，不能证明下一条源码语句一定是触发异常的指令。**

因为阶段 A 完全没有 Hook，本轮不再重复怀疑 Dialogue 地址、字体调用、D3D9 或 NativeLooseAssets v0.9 的内存补丁冲突。

## 二、确认的底层根因：自制 `_chkstk` 不符合 x86 ABI

在 v0.1b 的**实际编译机器码**中，工作线程包含：

```asm
mov eax, 0x1110
call _chkstk
; 调用后直接访问栈中的局部变量，没有第二条 sub esp, eax
```

递归目录遍历函数还会以 `0x164C`（5708 字节）调用同一个辅助函数。

但旧版自制 `_chkstk` 只逐页读栈地址，不调整 ESP。Clang-CL 对这条内置运行时调用的约定要求辅助函数在探测保护页的同时**实际将 ESP 移动到新栈帧顶部**，并保持必要的调用现场。二者不匹配会导致局部变量覆盖尚未分配的栈位置及调用现场。

这是根据源码与机器指令可以独立证明的严重实现错误，足以解释阶段 A 的崩溃风险；但由于没有故障现场转储，不能把具体 Windows 异常码或唯一原因凭空写死。

## 三、修复方法

仅修改独立 NPC 插件内部的 `_chkstk`，不修改 `Bond.exe` 或任何游戏资源：

1. 保存原 EAX、ECX、EDX，以及编译器传入的返回地址。
2. 按页逐步探测目标栈区，避免直接越过系统的保护页。
3. 按要求计算 `T = 调用前 ESP - 栈帧大小`。
4. 在新栈帧顶部暂存原寄存器和返回地址，将 ESP 移动到新位置。
5. 依次恢复寄存器，执行 `ret` 后，ESP 恰为 T，且可返回原调用点。

原生 LOC 索引逻辑、对话语义分流、字体代码和 D3D9 Hook 均没有改动。

为了进一步区分潜在的其他初始化故障，在 `MODULE_PATH_OK` 后额外记录 `BEFORE_LOG_PATH` 和 `LOG_PATH_READY`，再尝试创建正常日志。

## 四、编译及离线验证

- 已使用 Clang-CL/LLD 实际编译 Win32/i386 DLL：`release/NPCSubtitles.asi`。
- `source/NPCSubtitles/tools/verify_stack_probe.py` 解析最终 PE 的 `.text`，定位 `_chkstk` 的入口和返回段，再核对编译器生成的两个大栈帧 CALL 的目标。
- 两处调用分别来自大小为 `0x1110`、`0x164C` 的栈帧；检查栈迁移及寄存器恢复序列。

本包 `release/NPCSubtitles.asi` 只编译 `NPC_DIAG_STAGE=1`，没有实际 Dialogue、Glyph、Resource、D3D9 Hook，也不产生 NPC 字幕。

3. 启动游戏，检查能否正常进入菜单。三个日志始终位于当前 NPC ASI 所在目录。
