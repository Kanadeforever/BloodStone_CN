## 三、已确认的运行时位置和数据结构

| 项目 | 已知位置 / ABI | 来源 / 用途 |
|---|---|---|
| 原生 Dialogue CALL | 静态 VA `0x0093A2A1` | NPC 字幕唯一已验证捕获入口 |
| Dialogue 目标 | 静态 VA `0x00F12820`，调用哈希传参 | 传入 `*_script_dialogue.loc` 键的 hash |
| 原生字形查找槽位 | 静态 VA `0x011A02D8` | 按 UTF-16 单元、variant、scale 查字形 |
| 字体资源解析 CALL | 静态 VA `0x00E42C21` | 取得资源对象内的 D3D9 纹理 |
| Font 的资源句柄 | `font+0x12C` | 关联 font 对象与纹理句柄 |
| 资源对象纹理位置 | `resource+0x08` | 获取 `IDirect3DTexture9*` |
| 本体指纹 | PE timestamp `0x4CA36144`、SizeOfImage `0x010CC000` | 用于阻止错误版本的地址写入 |

这些地址及指纹与用户 2026-10-04 `Bond.unpacked_analysis.exe` 明文运行时转储一致。加壳的磁盘 `.text` 不直接用于验证 CALL 指令；必须在运行时解密完成后再安装代码补丁。源码沿用 P1b 已实机成功的单一 Dialogue Callsite 及 Hook 协议。

原有 R10.2 实机日志已经验证 Monaco `NPC_DIALOGUE_EVENT index=HIT` / `NPC_SUBTITLE_HIT`；N3 独立 D3D9 字幕曾实机可见。**旧的 raw SubmitText 0x00E85900 创建新字幕未显示**，永久不恢复。不得附加另外两处重复 Dialogue CALL，也不得用正文 substring 判断是否 NPC。

## 四、本版架构

```text
用户已运行的 NativeLooseAssets v0.9（原版 PAK，EN 中文 LOC/原生 EUR 中文字库）
                         │
                         ├─ BSCNContents/loc/**/*_script_dialogue.loc
                         │          ↓ 精确 hash + OLTX EN UTF-16LE
                         │      DialogueIndex
                         │          ↓
Bond Dialogue CALL 0x0093A2A1 → 原始事件 +0x1C 分流
                                             ├─ 0/无效 → 禁止重复字幕；0 时清空旧队列
                                             └─ 1 → policy → 三行 FIFO 队列
Bond 游戏事件 0x00E46E70 → CutSceneStart/End → 清空/恢复同一个队列
                                                            ↓
原生 EUR 字形函数及 D3D9 纹理 → Unicode glyph/UV/advance → EndScene 前字幕绘制
```

LOC 由 NPC ASI 从它自身旁边的 `BSCNContents/loc` 读取，其他资源位置不是硬编码的。实际中文文本仍由主汉化统一的 86 份 JSON/LOC 提供，NPC 不持有另一套翻译。当前有 3 个原生 EUR 字体面，它们已经在 NativeLooseAssets v0.9 下实机确认可用于中文显示。

NPC 的代码只读取/引用游戏自己创建的字体纹理：内部获取字形快照后按 Unicode BMP 码点查找相应的 UV/advance，使用 D3D9 DrawPrimitiveUP 绘制字幕。为了保护渲染期间的纹理生命周期，缓存持有 COM 引用，重置前释放；每帧快照另加引用，Draw 完毕后释放。

**当前分流不使用语义签名表。** `4DF2884F108C89CD→NATIVE` 仅是历史实验签名，已被实机验证的 `+0x1C` 原生分流取代。当前版本不读取 TSV。

## 五、运行时路径硬规则

```text
任意受 ASI Loader 扫描的目录/
  ├─ NativeLooseAssets.asi         ← 已实机成功的主汉化（通常同目录）
  ├─ NPCSubtitles.asi              ← 本项目实际输出
  ├─ NPCSubtitles.log              ← 仅 Bond.exe --log 时生成

```

上述“同目录”是唯一固定相对位置，绝不把 `scripts` 或 `plugins` 当成游戏用户必须安装的位置。源码不再读取 `NPCSubtitles.ini`；当前显示基准为：480p Scale 0.43、随视口非线性增长、BaseY 0.14、MaxWidth 0.76、最多三行；当前可同时绘制最多三条独立 NPC 字幕。v0.1e 的行高、基线、字形亮度混合及 640×480 至 4K 缩放均已通过用户实机测试。

## 六、D3D9 生命周期与性能

- 首次装载时独立 Hook Bond 的 `Direct3DCreate9` IAT，chain 调用已有实现，不改变主汉化 v0.9。
- 接管已验证的 `IDirect3D9::CreateDevice[16]`、`IDirect3DDevice9::Reset[16]` 与 `IDirect3DDevice9::EndScene[42]`。
- 绘制应发生在原始 `EndScene` 调用之前（有效的 BeginScene/EndScene 范围内），绘制前 Capture StateBlock、绘制后 Apply，防止影响 HUD。
- 旧 v0.1 会创建临时 Direct3D9 接口并改写其 CreateDevice 虚表；v0.1a **完全取消**此路线，只允许从游戏自身创建的真实 Direct3D9 对象挂钩。因此如果游戏的 Device 已在插件加载前创建，本版暂时无法保证追踪到已有 EndScene。
- Reset 前清空纹理缓存与状态块；重置后继续等待原生字形/资源捕获，避免使用失效 GPU 对象。
- 无活动字幕时检查时间戳直接返回，活动字幕每个 Device 复用一个 StateBlock。当前使用固定大小的静态字幕文本缓冲区，避免每帧动态字符串内存分配。

## 七、配置、调试日志、验收

当前只提供一个正式可部署文件：`NPCSubtitles.asi`。没有 INI、BFA、BLI、重复文本库、游戏文件或替换版 PAK。

需要提交故障报告时通过 `Bond.exe --log` 开启日志；普通启动不写日志。优先检查以下事件：

- `NPCSubtitles v0.1 STARTING`：插件已加载并执行工作线程。
- `NPC_DIALOGUE_INDEX_READY`：日志的 `first` 是成功解析的 LOC 数，`second` 是索引记录数。
- `NPC_DIALOGUE_HOOK_READY`：唯一有效原生 CALL hook 安装成功。
- `NPC_NATIVE_GLYPH_CJK_DRAW`：有原生中文 UV 数据参与 D3D9 绘制；视觉可见仍需实机确认。
- `D3D9_IAT_HOOK_READY`、`D3D9_DEVICE_HOOK_READY`：确认独立 D3D9 链已安装。
- `NPC_SUBTITLE_QUEUE_HASH`：对白 hash 精确命中并进入当前显示队列。
- `NATIVE_FONT_CAPTURE_WAIT`：已有字幕但还没找到原生纹理，需检查 Hook 时序或句柄映射。
- `DEVICE_RESET_RELEASED` 与 `DEVICE_RESET_COMPLETE`：设备重置时释放纹理、完成调用；重置后是否继续绘制仍要实机确认。

**历史阶段已有 Win32/x86 链接结果和 PE 校验**，不能代替当时的 Windows 实机测试，更不能据此证明 NPC 中文字幕可见。第一次实机优先确认显示链，其次检查分辨率/帧率/多对白/字幕重叠情况。

## 十一、2026-10-10 v0.1a 启动崩溃阻塞与诊断候选

最新实机结果是 v0.1 编译版无法启动：用户报告与 NativeLooseAssets v0.9 同时运行时，Bond.exe 内存约 3 MB 即崩溃，插件没有任何日志。此前的“编译和静态验证通过”不构成 Windows 启动兼容性证明。

已复核旧二进制：`SizeOfImage=0x0034C000`，大量静态预留 `Entry[4200]` 导致该 DLL 的虚拟映像达到约 3.3 MiB。该尺寸不能和进程工作集直接划等号；只是可修正的静态映像结构问题。现在正式功能版改为启动日志建立、游戏 PE 指纹核对后用 `VirtualAlloc` 申请索引内存，使自身映像缩小为约 196 KiB。旧 `Direct3DCreate9` 临时对象探测也已经删除；此前它可能与第三方 D3D9 wrapper 的动态虚表生命周期冲突，但没有异常转储，**此推断并未证实**。

本版同时提供两个真正的 Win32/x86 PE32 DLL：`release/启动诊断版/NPCSubtitles.asi` 为不安装任何 Hook 的极小启动探针，输出 `NPCSubtitles_boot.log`；`release/NPCSubtitles.asi` 为修正后的完整功能候选，输出 `NPCSubtitles.log`。两者绝对不能同时安装。用户保留已经成功的 NativeLooseAssets v0.9 和所有原生 PAK / LOC / 字体内容，先测试无 Hook 诊断版，确认能正常启动后才切换功能候选。诊断分支详见 `docs/启动崩溃排查与安全回退.md` 和 `docs/安装及测试说明.md`。

该 v0.1a 只是安全性和诊断候选，未通过用户 Windows 实机验收，不能标注为“启动崩溃已修复”或“NPC 中文字幕已显示”。下一个有效结论应由新日志与游戏实际启动状态产生，不再依靠静态 PE 校验猜测。

## 十一、v0.1c：修复自制 `_chkstk` 的编译器 ABI 违例

用户 v0.1b 阶段 A 实机反馈：游戏崩溃，启动日志最后为 `WORKER_THREAD_CREATED`，阶段日志最后为 `MODULE_PATH_OK`。阶段 A 完全未安装 Hook，因此不能把它归因于与 NativeLooseAssets v0.9 的代码补丁冲突。

对**实际生成的阶段 A PE32 机器码**分析发现，工作线程调用 `_chkstk` 分配 `0x1110` 字节局部栈空间，递归 LOC 目录枚举调用 `_chkstk` 分配 `0x164C` 字节。调用者在 `_chkstk` 返回后不会单独修改 ESP。旧自制 `_chkstk` 只探测而没有分配，导致 ESP 失配并威胁调用现场。

新的 `_chkstk` 实施页探测、移动返回地址及寄存器、调整 ESP、恢复寄存器再返回，确保编译器要求的栈帧真正建立。专用 `tools/verify_stack_probe.py` 对已经链接的最终 PE 做机器码验证：两处编译器调用目标、恢复寄存器序列和 ESP 迁移均匹配。

本轮没有动 Dialogue、Glyph、D3D9 的运行逻辑，也没有动主汉化 v0.9；`MODULE_PATH_OK` 之后增加 `BEFORE_LOG_PATH`、`LOG_PATH_READY` 两个细分日志，用于对尚未经过实机的情况继续定位。

### 明文 EXE 逆向证据

对应 PE TimeDateStamp `0x4CA36144`、SizeOfImage `0x010CC000` 的原版明文 Bond.exe：

- `0x0093A26C`：读取原始对白事件 `[edi+0x1D]` 并将零值判断结果写入 `[esi+0x79]`。
- `0x0093A282`：读取原始对白事件 `[edi+0x1C]` 并将零值判断结果写入 `[esi+0x7A]`。
- `0x0093A2A1 -> 0x00F12820`：现有 NPC 文本查询 Hook，位于原生文本 UI 分支之前。
- `0x009302D5`：根据 `[esi+0x7A]` 进入或跳过原生 UI 提交路径；`+0x79` 还有独立条件作用。
- `0x0093039D -> 0x00E46E70`：游戏自己的 UI 提交 CALL；捕获该站点只能证明调用发生，不能证明字幕实际显示。

### 本轮实现

在现有 Hook 下直接安全读取 EDI/ESI 关联的原始事件和派生字段，输出 `ORIGINAL_DIALOGUE_EVENT`。仅在 `Bond.exe --log` 模式、且原游戏 CALL 指令与目标严格匹配时，安装第二处观测 Hook，输出 `ORIGINAL_NATIVE_UI_SUBMIT_CALL`，随后恢复现场并以尾跳转执行原函数，完全不修改返回值或游戏文本数据。

两个日志记录同一对白哈希与对象地址、毫秒时间，可以用于实机判断原始事件是否进入原生 UI 通路；但未知事件类、未经过该 UI 的字幕以及其他显示通路仍不能凭静态分析排除。无 `--log` 运行时不会安装第二处 Hook，也不会创建或更新三份日志。

### 游戏版本、事件及调用约定

继续沿用游戏 PE 时间戳 `0x4CA36144`、SizeOfImage `0x010CC000`，原生 NPC CALL `0x0093A2A1`、字形槽位 `0x011A02D8`、字体资源 CALL `0x00E42C21` 和既有 D3D9 Hook 均不变。独立反汇编游戏自身的 `0x00E46E70` 事件派发函数，开头 8 字节应为 `56 8B F1 E8 68 10 6A FF`，最后一条 CALL 目标 `0x004E7EE0`。游戏事件名称表与实际消息发送点证明：

- `CutSceneStart`：事件 ID `0xA2193087`，例如游戏的 `0x00B4860D` 与 `0x00BE2ACF` 会构造该消息并通过 `0x00E46E70` 派发。
- `CutSceneEnd`：事件 ID `0xA2193088`，例如 `0x00B48654` 会构造该消息并派发。
- 上述消息结构首个 `U32` 是事件 ID，首个调用参数为消息对象指针。调用方式是原生 x86 thiscall，`ECX` 传派发对象，栈上另有两个原始参数。

在 `0x00E46E70` 安装一个校验过前 8 字节的 JMP；分配最小的 Win32 执行跳板，搬运原始 8 字节并修正其中 CALL rel32，然后跳回 `0x00E46E78`。入口仅比较两个事件 ID；非过场消息不进入插件 C++ 回调。命中事件时，保存并恢复所有通用寄存器与 EFLAGS，再继续原游戏派发逻辑，不修改游戏的消息参数、声音、画面和 UI。由于它是游戏事件总线而非历史额外原生 UI 提交 Hook，影响手柄图标或游戏帧率的风险仍需实机复验，不能仅凭静态设计视为无风险。

### 生命周期与线程约束

- 启动事件：原子设置 `g_cutscene_active=1`，在短锁内执行 `subtitle_queue::Clear`，清除最多三条可见字幕和十六项等待消息，同时重置去重哈希。
- 过场期间：`Draw` 快速退出、不绘制字幕；`AfterDialogue` 在入队前和拿到队列锁后分别检查过场标志，避免竞态插入。
- 结束事件：原子设置 `g_cutscene_active=0`，不恢复已清掉的旧字幕，新 NPC 对话可重新显示。
- 辅助机制：即便个别过场未及时发出启动消息，只要观察到游戏原生剧情对白 `+0x1C=0`，就清除尚未到期的环境 NPC 文字和等待队列。该机制不能保证无对白的所有过场都会触发，不能冒称全面覆盖。
- 只在显式 `Bond.exe --log` 时记录 `CUTSCENE_NATIVE_EVENTS_HOOK_READY`、`CUTSCENE_START_QUEUE_CLEARED`、`CUTSCENE_END_QUEUE_RESUMED`、`NATIVE_DIALOGUE_QUEUE_CLEARED` 和相应统计，不额外创建配置文件或 TXT/TSV。

### 编译、检查、状态与下一步

本轮基于用户已经实机成功的 v0.1e-log5 修改活动源码 `src/native_standalone.cpp` 与 `src/subtitle_queue.h`，新增过场回归测试。使用包内 `source/NPCSubtitles/tools/build_clang_cross.py` 实际生成 PE32/x86 `release/NPCSubtitles.asi`，检查 Win32 栈探测、Hook 入口和机器码、独立 C++ 队列清空/恢复测试。更新 docs 与构建说明，所有源码和正式文档 UTF-8 无 BOM、CRLF。正式发布包根目录严格为 `docs/`、`source/`、`release/`、`.build/`，源码、脚本、当前 ASI 与全部已知逆向信息独立完整，参考源码 ZIP 随包保存。
