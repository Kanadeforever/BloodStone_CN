# NPCSubtitles v0.1 编译及逆向复核记录

## 实际构建路径

编译器：`clang-cl`，目标三元组 `i686-pc-windows-msvc`；链接器 `lld-link`；运行平台为 Linux 交叉构建环境。发行物：`release/NPCSubtitles.asi`。Kernel32 导入库由本包 `tools/kernel32.def` 临时生成；Direct3D9 通过游戏现有 D3D9 接口和虚表访问，不需要 d3d9.lib 或独立 d3d9 DLL 文件。PE 使用 `/Brepro` 固定构建元数据。

旧源代码的 `#include <windows.h>`、`#include <d3d9.h>`、大量 STL 与 SDK 依赖无法直接在当前容器编译，无法在没有 Windows SDK/MSVC 库的情况下直接链接。为提供可实机测试二进制，新活动源码写明最小 Win32/D3D9 ABI 并重实现实际所需行为。历史源码原样归档保留。**这是有独立功能边界的重实现，不是把旧 18 个 cpp 原样编译成功。**

## 逆向位置

- PE ImageBase `0x00400000`，timestamp `0x4CA36144`，SizeOfImage `0x010CC000`。
- 原生 Dialogue 指令 `0x0093A2A1`：真实明文指令 `E8 7A 85 5D 00`，目标 `0x00F12820`。
- 字体资源调用 `0x00E42C21`：真实明文指令 `E8 AA F8 03 00`，目标 `0x00E824D0`。
- 原生字形 slot `0x011A02D8`，font resource handle offset `+0x12C`，resource texture offset `+0x08`。字体 ABI 从上传的独立项目基线继承，尚须新插件实机验证。
- 只 Hook `0x0093A2A1`，禁止触碰另外两处重复 NPC callsite。

## LOC 样本

历史原生 LOC 数据集合内存在 23 份 `*_script_dialogue.loc`。模拟当前索引规则（EN 语言块、严格 key table、hash 关联）获得 22 份可解析、1 份无法安全定位 key table 的结果，共关联 1480 项 EN 文本；这与以前记录的部分解析结论相符。存在异常的原始文件不作为整个插件初始化失败理由。实际游戏应读取 NativeLooseAssets v0.9 已成功的 LOC，而不是把这套历史资源覆盖到游戏。

## 自检层级

1. Win32 DLL 架构、机器码、导入表、PE 入口：编译后的二进制检查。
2. 运行时源码自检：对话地址、内置 P1b 语义签名与机器码、中文码点字形、原生 LOC、Reset、用户目录与版本。
3. 从压缩包独立解出后重新构建和 SHA-256 对比：确保不依赖之前工作目录。
4. 游戏实际加载与画面显示：**只能由 Windows 实机提供，当前尚未完成。**

## 当前已知限制

D3D9 的 IAT/vtable Hook 是链式处理，仅通过真实游戏创建的 Direct3D9 接口建立设备 Hook；已删除临时 Direct3D9 接口探测。若在游戏 Device 已经创建后才载入，此构建不能保证截获既存 EndScene；日志会显示没有 `D3D9_DEVICE_HOOK_READY`，需后续专项处理，不能拿原有字幕不显示直接判断 LOC 或字体失败。

字幕绘制目前为单条活动字幕、最多三行，固定约 `0.56` 视觉缩放、屏幕上方约 14% 的位置。它保留事件精确匹配、NATIVE 签名抑制和原生字库使用路线，但**不保证与旧 P1b 的所有排版/调度细节等价**。

## v0.1a 双版本构建与加载阶段审查

- 原 v0.1 ASI 的 PE `SizeOfImage=0x0034C000`，其中 `Entry[4200]` 的静态字幕文本占据大部分虚拟映像。该数字与用户报告的“内存 3 MB”不能直接对应，更不能用于确认崩溃原因。
- v0.1a 将索引内存移到日志初始化与游戏版本确认之后的 `VirtualAlloc`，编译后的新 PE 映像远小于旧版。
- 诊断 ASI 和功能 ASI 采用相同的 Win32/i386/Kernel32 技术栈，但各自独立构建：诊断 ASI 只有 DLL 加载日志，不引用游戏地址、D3D9 或资源 Hook。
- 禁止以功能候选离线编译通过冒充 Windows 启动通过。首次测试严格按 `安装及测试说明.md` 分阶段执行。



## v0.1c ABI 复核

Clang-CL 实际编译生成 PE32/x86 阶段 A 后，`tools/verify_stack_probe.py` 在 `.text` 中查到 `_chkstk` 的 ESP 调整、寄存器恢复指令，并反向验证两个由编译器产生的 `call _chkstk`。过去仅探测保护页而不更新 ESP 的逻辑已经取消。全部验证为**静态验证**，仍需要 Windows 实机启动确认。


## v0.1e 最新编译验证（2026-10-10）

Clang-CL/LLD 直接生成 Win32/x86 `release/NPCSubtitles.asi`；根据真实游戏 v0.1d 可见截图修改的是 `Draw()` 和 `Configure()`，不改变已验证的 `0x0093A2A1`、`0x011A02D8`、`0x00E42C21` 或 D3D9 Hook 安装站点。

测试涵盖亮度混合数学模型、分辨率缩放比例与中英字形基线、查无 hash/主动排除 hash/冲突 hash 区分。视觉成败要等待用户本机 GPU 实测，不以 PE 与单元测试代替。

## v0.1e-log2：规则内置与二进制确认

仅内置 `4DF2884F108C89CD → NATIVE`。Clang/LLD 会把 64 位签名比较优化成两条相邻 32 位 XOR 指令，因此二进制测试检查真实指令与两半的立即数，而非错误要求整个 64 位常量在 `.rdata` 连续存放。检查同时要求二进制不包含旧 TSV 文件名或读取逻辑、仍为 PE32/x86 DLL。此项仍属于静态验证，实际语义抑制须以 `Bond.exe --log` 的运行事件及画面验证。
